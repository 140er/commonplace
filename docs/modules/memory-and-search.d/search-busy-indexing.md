- **Owns:** What `GET /api/memory/search` answers when the palace worker could not take the read within its bound because an index write held the palace: a 503 `{"error": "no: memory is busy indexing; try again in a few seconds", "retry_after_s": 2}` in about the worker's read bound (5 s by default), the same retry the Memory page already shows for a failed or timed-out source, never an empty result.
- **Promises:** A search never waits on the search-index job (or a person's own write) for longer than that bound, and it is not held back by a write that is only waiting; once the write ends the same request returns its results unchanged, so nothing is hidden for good. The startup-context step on `initialize` never touches the search path and is bounded at 80 ms on its own.
- **How it fails:** A busy answer is a retry, not a lost memory; any other worker failure keeps the generic refusal. The gateway keeps the worker's busy answer typed (`WorkerBusy`): MCP clients get `-32001` with `retryable` and `retry_after_s` (the code it already uses for a locked database), and the gateway's own tool calls and `call_memory_tool` raise it as a retryable busy error instead of the generic unavailable answer.
- **Tests:** `tests/test_commonplace_memory.py` holds the worker's lock and checks the bounded answer, then the unchanged results; `tests/test_search_lock_bounded_wait.py` checks the gateway mapping.
