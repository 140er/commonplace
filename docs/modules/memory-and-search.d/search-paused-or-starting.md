- **Owns:** What `GET /api/memory/search` (and every Memory route that reads the palace) answers while the memory worker is paused for an online backup, still starting, or busy: HTTP 503 `{"error": ..., "retry_after_s": N}`, plus `"warming_up": true` while a worker starts. The sentences are `no: memory is paused for a backup; try again in about N seconds`, `no: memory is starting; try again in about N seconds` and `no: memory is busy indexing; try again in a few seconds`. A request spends at most `COMMONPLACE_MEMORY_WAIT_S` (default 5 s, at most 60) in all its worker calls together waiting for a pause to end or a worker to start.
- **Promises:** A search never waits per worker call (it used to wait up to 20 s for a pause, once for every call it made, and a search makes several), so it answers within about that budget instead of running into its client's limit; once a call of the request met the pause the others do not wait at all. The worker start goes on in the background when the budget ends, so the next search finds it. Nothing is hidden for good: once the pause ends the same search returns its results unchanged. The same bound holds for MCP clients: `initialize` and tool calls answer `-32603` with `retry_after_s` while paused, and `-32001` with `retryable` and `warming_up` while a worker starts.
- **How it fails:** A pause longer than the budget is answered as paused (retry), never as an empty memory and never as a generic 403; a worker that cannot start at all keeps answering the generic unavailable error.
- **Tests:** `tests/test_search_stall_round2.py` pauses the supervisor and delays a worker start under the real route.
