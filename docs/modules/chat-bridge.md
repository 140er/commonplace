## chat-bridge

- **Paths:** `commonplace/chat_bridge/`, `tests/test_chat_bridge_foundation.py`, `tests/test_chat_bridge_identity.py`, `tests/test_chat_bridge_intake.py`, `tests/test_chat_bridge_confirm.py`, `tests/_chat_bridge_fake.py`
- **Owns:**

  - The foundation of the chat-platform bridge (`docs/design/chat-platform-bots.md`, card #455, slice 1): the workspace file `chat_bridge.sqlite3` (the whole schema of the note; opened like `bots.sqlite3`, created only by creating an install, so a read, an unknown id or an intake request never makes it), the install rows, sealed credentials, the owner install routes, the adapter's `test` seam, the read-only `bridge_status` tool and the kill switch (`commonplace bridge status|disable`). The package is `commonplace/chat_bridge/` because `commonplace/bridge.py` is the MCP client bridge.

  - `adapter.py` is the interface a platform implements (`platform`, `secret_fields`, `caps`, `test`, `verify`, `normalize`, `post`, `post_private`, `find_posted`) with a registry; `Inbound`, `Outbound`, `Target`, `PostResult`, `Verified`, `Challenge` and `Reject` are the only shapes that cross it, so platform vocabulary stays inside an adapter. Production ships no adapter yet, so creating an install answers `unsupported_platform`; tests register a fake in memory. `run_test` reduces any adapter answer or exception to one of a few codes with fixed sentences, so a platform's own error text never reaches a person, a log or an audit row.

  - `sealing.py` seals `secrets` as one AES-256-GCM blob with the install id as associated data. The key is derived per workspace (HKDF-SHA256) from the operator-provisioned wrapping key named by `COMMONPLACE_WRAPPING_KEY_FILE`, which must be a private regular file outside the data directory; without one, creating or rotating is refused (`sealing_unavailable`) and nothing is stored. `store.BridgeStore.secrets` is the only reader of the blob and no view, route, tool, log line or audit row carries it.

  - `index.py` is the hub-wide index in the control database (`bridge_install_index`: install id, workspace id, platform, team id; no secret, no text). It resolves an intake URL to a workspace later and makes a platform team installable once per hub, across workspaces. `service.py` holds the rules shared by the routes and the command line, and writes one `bridge.install` audit row per change (the action in the tool column, install id, a fixed reason code).

  - `routes.py`: `GET`/`POST /api/bridge/installs`, `PATCH`/`DELETE /api/bridge/installs/<id>` (`enabled`, `label`, `daily_cap`, new `secrets`) and `POST .../<id>/test`, for the signed-in workspace owner only. The public intake paths under `/api/bridge/in/` are routed so they are reachable without a session, and answer 404 for every install until the intake slice.

  - `links.py` is the identity slice (card #455, slice 2). `issue` gives a signed-in member a link code for an enabled install: 12 characters of a 31-letter alphabet, valid 10 minutes, one live code per person and install, returned once and stored only as a salted SHA-256 hash (`bridge_link_codes`). `redeem` is what intake will call with a platform user's text and the kind of message: only a direct message links, the same text in a channel burns the code, and wrong codes are counted per sender in `bridge_link_tries` (five, then a 15-minute lock; a code presented five times that could not finish is dead). `resolve` re-checks on every event that the install is on, the link is live and the person is still a member (`sessions.person_principal`); a link whose person left is ended there, so adding them back does not revive it. Links are one person and one platform id per install (unique in the file); unlinking sets `revoked_at` at once and drops the open prompts of that platform id; a revoked or stale row is replaced when the id or person links again.

  - Routes added: `POST /api/bridge/installs/<id>/link-code`, `GET /api/bridge/links` (own links, plus the enabled installs a member can link to), `DELETE /api/bridge/links/<id>` (own only), and for the owner `GET /api/bridge/installs/<id>/links` (platform id, person, email, still a member, time; no text) and `DELETE /api/bridge/installs/<id>/links/<link>`. Audit rows (`bridge.install`, tool `link_code`, `link`, `unlink`, `unlink_owner`, `link_end`, `code_burned`, `code_locked`) carry ids and fixed codes only, never a code or a platform id.

  - `intake.py` is the intake slice (card #455, slice 3): `POST /api/bridge/in/<install>/events` verifies (the adapter checks signature and freshness against the unsealed secrets, the team it names must be the install's team, else 401 with no row), filters (bots including the app itself, non-mentions, shared channels, unmapped channels, empty text: journaled `ignored`, still 2xx; a text that is only a link code is handled wherever it was said), journals into `bridge_events` (a duplicate `(install, event)` is answered 2xx and runs nothing), resolves the sender through `links.resolve` (no link: one fixed sentence, the text is dropped), applies the install's daily cap and starts the turn. Body cap 256 KiB, one token bucket per install. `POST .../interact` verifies, then hands a button tap to `confirm.py` (confirmation slice, below); `GET .../oauth` and every other path stay 404.

  - `turns.py` maps a linked person's message onto the Bots layer: a direct message goes to their General bot, a mention in a mapped channel to their project bot of the mapped project, stored with request id `bridge-` plus 32 hex of a hash of install and event (the Bots store's `(bot, request_id)` key is the second idempotency layer) and run by the ordinary `TurnRun` with surface `dm` or `channel`. A project the person cannot read has no bot for them, so no turn starts and a fixed sentence is posted. `resolve_events` closes what a restart left: an event still `received` after 30 seconds, and a `running` event with no live turn, which the Bots layer's own `interrupted` closes as a stored `failed:interrupted` reply that is posted once and never rerun.

  - `outbox.py` and `worker.py` deliver. Every reply is a `bridge_outbox` row whose `ref` points at the stored bot message (`reply:<id>`) or a fixed sentence (`text:<code>`), never a copy of text, split to `caps.max_text` into one row per part. A row goes `queued -> sending` by compare-and-set before the adapter is called and `sent` after; a definite platform failure (`PostResult.retry`) re-queues with backoff, at most 5 attempts, then `failed` (the stored reply is untouched); an exception from the adapter leaves `sending`, which the sweep turns into `unknown` and settles through `find_posted` or, without it, one fixed "may not have arrived" line (part -1). Disabling the install cancels queued rows; a turn that finishes after that is stored and not posted. The worker thread starts only once an install exists on the hub (at hub start or the first accepted intake); a hub that never installed the bridge starts nothing.

  - Channel mapping (owner only): `GET /api/bridge/installs/<id>/channels`, `PUT`/`DELETE .../channels/<ext_channel>` with `{board, disclosure?: titles|full, enabled?}`; the owner must be able to read the project, `titles` is the default. Audit tool names `map_channel` and `unmap_channel`.

  - `confirm.py` is the confirmation slice (card #455, slice 4): on a chat direct message nothing writes with the person's identity without their own tap. When the person's link has `confirm_ok` (their own opt-in, default off, `PATCH /api/bridge/links/<id>` with `{confirm_ok: bool}`, own link only, audited as `confirm_on` / `confirm_off`) the direct-message turn is offered the writing tools (`create_work`, `comment_work`, `tell_orchestrator`, `prioritize_work`, `remember`, `forget`) as confirm tools, so a call only freezes a pending action (the Bots confirm machinery: frozen arguments, server-built label, ten minute expiry, item version, compare-and-set consumption, the "your own words" check before any chip exists). `offer` queues each chip of the finished turn as a *private* outbox row (`target = private`, ref `prompt:<pending>`, one `bridge_prompts` row naming the platform id and channel it was shown in); the chip text is the pending action's label, redacted and clipped, two buttons carry only the pending id, and nothing the model wrote is in it. With `confirm_ok` off the routine writes are not offered, a confirm tool leaves its chip in the person's web thread and one fixed sentence says so. A channel turn stays read-only, so no chip can exist for a channel. `tap` handles the signed interaction: journaled once as `tap:<event>`, it runs `bots_turn.confirm` as the person only when the tapper's platform id and channel match the chip, the link is live with `confirm_ok`, the install is on, the person is still a member and the tool may be confirmed here; anything else is one fixed sentence to the tapper (a private post, never a channel post) and runs nothing; a second tap meets the compare-and-set (`tap_done`), a late one the expiry (`tap_expired`). The outcome (the stored event message, or "Cancelled.") goes back privately.

  - Web-only classes (open question 2, the note's recommendation): starting an agent, approving and creating a project (`start_work`, `approve_work`, `create_project`) are confirmed in the web app only, unless the owner allows them per install (`PATCH /api/bridge/installs/<id>` with `consequential_taps`, column `bridge_installs.consequential_taps`, default off, added to existing files on open). Everything else that confirms (running a command, sharing or forgetting what a bot learned) is never confirmed by tap. The outbox now posts a `private` row with the adapter's `post_private`; a private row cut off mid-send is settled like any other but gets no "may not have arrived" line.

- **Promises:**

  - A channel turn is narrower than a web turn and a direct message is not wider: the Bots engine gets `surface` and `disclosure` (see bots). The turn runs as the linked person only (`sessions.person_principal`, re-resolved on every event and every tool call), so a project they cannot read yields no bot, or the usual refusal, and nothing of another person's bot, thread or reply is read or posted.

  - Off by default at every level: no install exists until the owner creates one, a new install is disabled, and enabling needs a test that passed (`409 not_tested`). New credentials switch the install off and clear its test. Disabling (route or kill switch) cancels queued posts and open prompts of that install.

  - Anyone who is not the signed-in owner of the workspace (members, agent tokens, other workspaces) gets 404 on every owner route, and an unknown or foreign install id is 404 for the owner too; anonymous callers get 401. A workspace without installs has no `chat_bridge.sqlite3`, and the empty list is the owner's only answer. Deleting an install removes its rows in every bridge table and its index entry.

  - Credentials are write-only: validated against the adapter's `secret_fields`, sealed before they reach the store, never returned (a test greps responses, tool output, logs, audit rows and the raw files for a sentinel token). Platform ids are opaque text; the label is owner-typed (at most 80 characters) and never trusted.

  - Person routes are 404 for agents and tokens and for a workspace with no install, and for an install that is off; another person's link is a 404 like a missing one. A code is never repeated after issue: no response, log line, audit row or file holds it, and the account export writes the code hashes as `[redacted]`. Nothing here adds an agent tool: the tool lists are unchanged.

  - `bridge_status` (owner agent, trusted token, read only) is hidden, like an unknown tool, until the workspace has an install, so a workspace that never used the bridge sees the tool list it always had; once it has one it lists installs with the platform, label, on or off, tested time, mapped channel count and last intake time. No tool installs, maps, links or reads credentials. The command line never accepts credentials and `disable` creates nothing on a hub with no installs.

- **How it fails:**

  - Refusals carry a code and a fixed sentence: `invalid` (400, unknown fields included), `unsupported_platform` (400), `team_taken` (409, the team has an install in this or any workspace of the hub), `not_tested` (409), `sealing_unavailable` (503), `not_found` (404), `busy` (429). A failed test answers 200 with `ok: false` and one of `credentials`, `team_mismatch`, `missing_permission`, `unreachable` or `failed`.

- **Tests:**

  - `tests/test_chat_bridge_confirm.py` covers the clean workspace (no route, file, worker or tool-list change), `confirm_ok` off (writes refused, confirm tools wait in the web app, a forged tap does nothing), a write only after the linked person's own tap and exactly once (retry, double and concurrent taps), cancel, another person, a stranger, another place, another install, a switched-off link, an expired chip, a removed member, a revoked link and a disabled install, the person's own rights on the write, the chip text (server-built, names the action, no secret, not the model's words), comments, the owner's switch for the consequential classes, channels (no write tool, no chip) and the `confirm_ok` route.

  - `tests/test_chat_bridge_intake.py` (over real HTTP with `tests/_chat_bridge_fake.py`, an in-memory platform that signs, verifies and records posts, and a scripted chat model) covers the clean workspace (404, nothing created, no worker), an install that is off, forged, stale, foreign-team, malformed and oversized requests, an unlinked sender, a code sent in a channel, a DM and a mention turn with the tools and context each is given, the filter, a duplicate event (also concurrent) answered once, the asker's rights (a project they cannot read, no mixing between people), a removed member, delivery once with bounded retries and a failed row that keeps the stored reply, splitting, a post cut off between send and record, a restart mid-turn, a turn still running left alone, the daily cap and the owner channel routes.

  - `tests/test_chat_bridge_identity.py` covers the clean workspace and the off install, a code working once and only in a direct message, expiry, wrong tries and the lock, the sentinel check on a code across responses, logs, audit rows and files, one person and one install per link, unlinking at once, person and owner isolation, membership removal and the install switched off on the next event, deletion and the account export.

  - `tests/test_chat_bridge_foundation.py` covers the clean workspace (every route and the intake, nothing created), the unsupported platform, the sentinel leak check across responses, logs, audit rows and files, sealing (binding to the install, per-workspace keys, a missing, loose or misplaced key), enabling only after a test, rotation, the team unique across workspaces, owner-only access, input validation, delete, the audit rows, the kill switch and status (store, command and tool).
