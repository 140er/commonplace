- **Owns:**

  - Notes and filing for meeting-join bots (`docs/design/meeting-join-bots.md`, section 8). `notes.py` turns a finished meeting's stored segments into generated notes (summary, decisions, action items, open questions) on the model the owner configured for chat; `notes_store.py` is a mixin of `MeetingStore` with the segments, the note runs (`meeting_note_runs`, one row per meeting: state, code, attempts, counts, no text), the review edits, the filing claims, the transcript and meeting deletion; `filing.py` holds the inviter's two taps (keep a note in memory, approve an action as a card). The routes are in `routes.py`. Writing the segments (capture and transcription) is a separate slice: this one reads whatever `meeting_segments` holds.

- **Promises:**

  - Notes are made while the meeting is `processing`, from its segments, one model request per batch of segments with no tools: the transcript goes to the model as quoted JSON data after the redaction. The owner's chat model is used as configured; a hosted model is refused unless the owner switched on `external_model_ok`, and no model, no budget, a failed or malformed answer means no notes yet: nothing is stored, the segments wait, the beat retries up to three times (ten minutes apart) and a 24 hour sweep deletes segments that were never turned into notes (and are not a kept transcript).

  - Every stored note has evidence that exists: segment ranges inside the batch, with their offsets. The server drops an item with a missing, empty, backwards or invented range, an unknown field or kind, over-long text or a second summary in a batch, and keeps an item but drops the speaker when the cited segments do not carry that speaker (a mixed stream carries none, so nothing is ever attributed to a person it cannot name). Text passes the redaction before it is stored. Notes are stored as drafts (actions as `proposed`), labelled generated, with the model that wrote them; an edit makes the text the inviter's (`origin: edited`), a dismissal ends it. A stop that lands while notes are made discards the notes with the segments.

  - Segments are deleted for real right after the notes are written unless the transcript is kept, which needs both the owner's `transcript_ok` and the inviter's per-meeting tick; the owner taking the allowance back stops the transcript being served and lets the sweep delete it. A kept transcript is served only to the inviter, labelled as other people's speech, and can be deleted alone; the notes stay. Deleting a meeting (only once it ended) deletes everything it owns and returns the list of what the inviter filed, which stays theirs.

  - Nothing is filed without the inviter's tap. *Keep* writes one drawer through the person's own memory save (secret scan and write rights included) into the wing they name or their `notes_wing`; with neither it is refused rather than filed somewhere shared. *Approve* creates one card through the same chat-task path a person's own chat uses, on a project they name and may write to, keyed by the note's own id. Each carries its provenance (generated by the notes bot, which meeting and day, which model, which segments, approved or kept by whom, edited by them if so). A double tap, a retried request and a replay after a crash file once: the note holds one claim per request, a drawer is keyed by its content and a card by the note. A refused write (a wing or project the person may not write, a secret) leaves the note open.

  - Only the inviter can do any of this: another person's meeting or note, the owner, an agent token or another workspace gets 404 before anything is read. Off until configured: with meetings off every one of these routes is 404 for members and 409 `meetings_disabled` for the owner, and no model is ever asked.

- **How it fails:**

  - Refusals carry a code: `not_open` (a note already filed or dismissed), `filing_in_progress`, `wrong_kind` (409); `choose_wing`, `secret_detected`, `cannot_file` (409); `meeting_active` (409); `invalid_text`, `invalid_request_id`, `invalid_board` (400); `no_transcript` (404); `not_allowed` (403, the inviter can no longer write in the workspace). Generation failures are codes on the run (`needs_configuration`, `needs_turn_on`, `key_missing`, `hosted_model_not_allowed`, `limit`, `rate`, `schema`, `model`, `timeout`, `http_error`, `bad_response`), never text from the meeting or the model.

  - Not built here: capture and transcription (the segments), a reduce pass over the per-batch summaries of a very long meeting (at most ten batches are read, the run says `partial`), in-meeting answers and the first provider adapter.
