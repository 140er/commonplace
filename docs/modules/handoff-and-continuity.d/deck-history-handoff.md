- **Owns:** `handoff/deck_start.py` and its route `GET`/`POST /api/handoff/start` (in `handoff/api.py`): what the Deck may offer for a stored thread, and the request for a handoff from it.
- **Promises:** The route adds no storage and no permission. `GET ?thread=` is for a reader of that stored thread (anyone else gets the same 404 as a missing thread) and says `ready`, with the live thread that carries the work on (the successor its own handoff registered), or `unavailable` with a plain reason and next step: no launch authority (`can_launch`: a signed-in person, or `handoff:write` with trusted trust), saved without a handoff, new thread not started or registered, a later thread already continues it (linked only when readable), or Handoff switched off for that agent and card. `POST` without `confirm` is a dry run: it names the destination and counts the saved chain that stays linked, and returns no checkout or transcript path. `POST` with `confirm` runs the same `ManualHandoff.start` as the `handoff_start` tool with `require_binding`, so launch authority, workspace binding, settings and idempotence are unchanged. Both calls pass the rules check as `handoff_start`. Verbatim history is only counted and named, never summarized; the optional note is stored exactly as typed.
- **How it fails:** A refusal is `{error, next_step}` (400 invalid destination or request, 403 no launch authority, 404 unreadable or missing thread, 409 handoff off, checkout not bound, another handoff running, or T3 unavailable); the old thread keeps running unless the answer says it was stopped. A start whose new thread began but whose old thread could not be stopped answers `source_settled: false`, and repeating it only retries the stop.
