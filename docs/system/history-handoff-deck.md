### History chains and handoff in the Deck

Decision: a person opens a saved thread and its chain, and requests a handoff, from one named page ("Saved threads", linked beside Map on the Deck Memory page) instead of new storage or a second handoff path. The chain and thread reads are the existing `/api/threads/<id>` and `/chain` routes. The only new route, `/api/handoff/start`, starts nothing the `handoff_start` tool could not: it calls the same `ManualHandoff.start` with the same launch authority, workspace binding and settings, and passes the rules check as `handoff_start`.

The page starts from a stored thread, not a raw local thread id: the thread that carries the work on is the successor that thread's own handoff registered, so a person cannot name an arbitrary thread on the host. The action appears only when the server says it is `ready`; everyone else reads the history with one plain sentence about why there is no action. Every unavailable or failed state gives a reason and a next step, a review step shows the destination and what is carried over before anything starts, and verbatim history is counted and named, never summarized. A dry run returns no checkout or transcript path, and only a 401 reads as signed out.
