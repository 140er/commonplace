### Memory map mode and private visibility

Memory offers a Map mode from the workspace view (the classic toolbar or the Deck Memory filter bar) or a Space's project-filtered Memory link. It reuses the existing canvas controller, theme/week filters, Map/Themes/People layouts and source side panel. A server-side theme parameter scopes acquisition before counts and limits. Navigation disposes the canvas and stale requests cannot reopen it.

For person sessions, only a current workspace-owner role read from the control database permits private data in map graph or selection responses. Missing or failed role proof hides private wings, private drawer metadata, private/secret fact relationships and private linked cards. Hidden data yields the same graph as absent data. Members may lose their own private memories in the map until per-user ownership is available; a short non-owner notice states this. Connection scopes, policy objects and other Memory reads keep their existing behavior.

Map citations are checked against the current workspace handoff store, including direct fact sources and every fact_sources row. For non-owners, private or unresolvable threads exclude the fact and null the selection source or thread-valued topic without removing keys. Request-local caches bound repeated thread/drawer citation lookups. Orphan people retain their existing visibility, unreadable themes look absent, and opening the map refreshes the person identity used by its notice.

Non-owner map facts also fail closed on missing, refused or failed drawer lookups and on thread-valued drawer rooms or origin/approval references. Ordinary non-thread reference values do not suppress facts. A null topic is an accepted visible distinction from normal topics such as general, without exposing the thread identity. The identity refresh has a 10-second deadline and starts without delaying the graph request. Pending, rejected or null identity retains the notice; only current-epoch owner proof clears it. Navigation or disposal prevents late identity updates. Thread references use their first path segment for bare IDs, application links and thread URLs; later path segments naming thr_ or mcp: thread forms remain checked, as do raw embedded private IDs. Reference decisions as well as thread lookups are memoized only within the current map request.
