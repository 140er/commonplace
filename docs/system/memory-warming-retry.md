### The Memory page waits out a warming or busy memory

The server now answers a memory search that meets a paused, starting or busy memory with a retryable 503 (`retry_after_s`, plus `warming_up` while a worker starts) in a few seconds instead of letting it run into the client's limit. The Memory page ignored the hint: a 503 on the notes source counted as a failed source and showed "Some sources could not be searched" or "Memory is taking too long to answer", so a person saw a failure for what is a short wait.

Decision: the page treats a 503 with a numeric `retry_after_s` on the notes search as a wait, not a failure. It shows one plain line ("Memory is warming up, retrying in N s" or "Memory is busy, retrying in N s"), keeps the typed query and the results on screen, and searches again after the stated time, capped at 10 s per wait and at 3 retries. One search is in flight at a time, so a retry cannot become a request storm, and a new query, the Try again button or leaving the page cancels a pending retry. After the last retry the existing message and Try again button appear. The retry lives in the page, not in the shared request helper, because only the Memory search has a visible wait line and other callers must keep failing fast. A 503 without a hint is not retried: it carries no promise that waiting helps. The line is a status element updated in place each second, so a person typing is not interrupted by a redraw.
