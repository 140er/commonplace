### Auto-addressed PR review comments: a Coworker picks up what a reviewer wrote and answers it (design note, card #613)

This note belongs to the Boards, Coworkers and Pipeline sections. It is a design and slice plan; nothing described here is built yet, and every "will" below is a plan, not a fact about the running app. Today a reviewer (a person or a review agent) leaves comments on a pull request, and someone has to copy them to the Coworker that owns the card, wait, and then look at GitHub to see what happened. The goal: a reviewer comments on the PR, the owning Coworker picks each comment up, changes the code, replies with a reason, or asks a question back, and the person sees per comment what happened, on the card in the Deck, without copying text between tools. It is item 2 of the parity goal (card #611).

#### What exists today (gap analysis, develop at the start of this note)

- **There is no way for review comments to reach Commonplace.** Nothing reads, stores or names a PR review comment anywhere in the code. A card carries `pr_url`, `pr_number`, `pr_repo`, `pr_state` (`open|merged|closed`), `pr_head` (full SHA), `pr_reported_at` and `checks` (`pending|passing|failing`), and all of them are reports written by the Coworker through the board tools (`BoardService._pr_report_updates`): a new `pr_head` clears `checks`, and a PR report stays unverified.
- **No inbound GitHub webhook exists.** `commonplace/webhooks.py` is the outbound side (signed deliveries of Commonplace events, a metadata allowlist, no payloads). The GitHub package (`commonplace/github/`) is a per-person, browser-only grant: Connect asks for no scope, the optional merge consent asks for `repo` for that one person's merge button, agents, bearer tokens and MCP receive no GitHub capability, and the hub holds no server-wide GitHub credential. Reading comments through a person's `repo` grant would give every comment read the reach of one person's account over every repository they can write to. That is the wrong tool.
- **The feed pattern exists and fits (reusable).** `commonplace/pipeline/` is an append-only, event-sourced store in its own workspace file (`pipeline.sqlite3`), written by a script on the production host through `POST /api/pipeline/events` with its own single-scope token (`pipeline:write`, minted with the token command, workspace-scoped, revocable, at most one live token). Events are idempotent by id, a request is validated whole and stored in one transaction, and secret-looking text is refused. The same shape carries comments. The pipeline's `cards.py` already answers "which visible card is this (repository, PR number)" with alias and rename rules, and the Pipeline view already shows a PR with its gate, check and merge steps.
- **Mapping a PR to a card is solved (reusable).** `pipeline/cards.py` `cards_for` uses the card's `pr_repo` (or its board's repository through `board_repos` when the card has none), repository aliases (`COMMONPLACE_REPO_ALIASES`), visibility of the reader, and refuses an ambiguous match: a PR number alone never establishes repository identity. The loop reuses that function, moved to a shared place, not a second copy.
- **Starting a Coworker on a card is solved, with one gap.** `runner/tools.card_start` starts a card on a machine through a fenced, capped job (`runner_jobs`, at most one live job per card, an hourly cap per machine, `launch_reason` texts, `start_retry` backoff for transient refusals). On a board with an accepted Coworker config (`[runner]`) the start runs through `orch/runner_bridge.fenced_start`, and `orch/triggers.py` already fires such starts from the board's own events with a cursor, a fence, a rebuilt requester, coded misses and bounded retries. A direct `card_start` needs a signed-in workspace owner or an allowed requester; there is no path for the hub to start a Coworker because "something happened on GitHub". The loop adds one trigger source to the existing sweep. It does not invent a second way to start work.
- **Who owns a card is known.** `tasks.assignee` is `conn:<name>` while a Coworker holds the card, `task_events` keeps every claim with its stamp, and a card's last start job (`runner_jobs`) records the machine, project and topic it ran with. The card's `branch` is the PR branch the Coworker owns. Reusing the last job's machine, project and topic is what makes the checkout and branch exist on the machine that is asked to fix the comment.
- **Card history exists, with a closed list of kinds.** `task_events` is append-only with kinds `add, edit, move, comment, claim, renew, release, expire, handoff, ask, decide, link, unlink` (a database CHECK; adding a kind is a migration). Counts and statuses can be written as `comment` lines; comment text must not be.
- **Needs me exists and takes questions.** A card with an `ask` (status `review`, `ask_options`, `ask_to`, `return_to`) lands in the owner's queue (`needs_me`, `/api/needs-me`, one Deck list shared by Today, Home, badges and the Board). `decide` records the answer. One card is one item however many things wait on it. That is exactly the "one Needs me item for the owner" the card asks for.
- **Deck card detail has section mounts (reusable).** `details.js` mounts per-card sections that fetch on mount and render their own empty, loading and failed states (`cardruns.js`: Runs with plain-word outcomes; `cardlinks.js`: agent and transcript links; `needs.js`: the PR panel with Open PR, Merge and its plain refusal reasons). `needs-me.js` is the one definition of "needs me". The Pipeline view (`deck-pipeline.js`) shows each PR as blocks; a comment count belongs there too.
- **MCP tools and scopes (reusable).** `LocalTool` in `commonplace/extensions.py` registers a tool with a `scope`, `kind`, `profiles` (`WORK_PROFILES`) and `available`; a new scope is added to `policy.SCOPES` and, for a feed token, to the gateway's single-scope route rule like `pipeline:write`. There is no profile named Coworker: differences come from `available=` and scopes. Previews (card #612) is the template for a store, service, routes and tools package with uniform 404, agent-token refusal on people routes, and a card note.
- **Redaction exists.** `commonplace/redact.py` (`redact`, `redact_value`, `find_kinds`) finds secret-looking text and secret-named keys. Log helpers (`http_util.log_failure`) record the error type, not the message.
- **Fix rounds.** The project rule is at most three fix rounds for a failing check, then ask the maintainer (`CLAUDE.md`, "Verification before a PR"); the project's review flow runs one gate per head and at most two fix rounds. There is no code that counts rounds, so the loop owns its counter.

#### What is missing

1. A store for review comments with one stable key per comment, an edit time, and a status per comment.
2. A way for comments to arrive without a GitHub credential on the hub.
3. A trigger that starts the owning Coworker when comments wait, and a way for that Coworker to read them and report one outcome per comment.
4. Rules and limits that keep the loop from merging, loosening checks, resolving other people's threads, dismissing a human review or pushing to a branch it does not own, enforced where the hub can enforce them and detected where it cannot.
5. The card, PR and Needs me views of all of it.

#### How comments reach Commonplace: the feed first, a poll as the fallback

The hub never calls GitHub and holds no GitHub credential. Comments arrive the way pipeline events do: a feeder process outside the hub reads GitHub and posts to one write-only route. Two modes share one route, one token and one payload:

- **Feed (preferred).** Where the production host already sees GitHub events, it forwards review events for watched repositories to the intake route within seconds.
- **Poll (fallback, and the first version).** `commonplace pr-review poll` runs on any machine that has a read-only GitHub credential. It asks the hub which PRs to watch (`GET /api/pr-review/watch`: the repositories and PR numbers of cards whose `pr_state` is `open` or unset, from boards where the loop is on), reads each PR's inline review comments, review bodies and conversation comments with conditional requests (an unchanged PR costs no rate limit), and posts what is new or edited. It polls every 2 minutes for a PR with activity in the last hour, every 10 minutes otherwise, and stops for a merged or closed PR. The same watch answer carries a `check_now` flag the owner can set from the Deck.

There is no inbound GitHub webhook on the hub: it would add a public, unauthenticated-by-session route with its own secret and signature handling, and the feeder already gives the same latency where it matters. If one is wanted later it only needs to call the same intake. The credential the feeder holds is read-only (pull requests: read, plus contents: read for the changed-file list). It lives on the feeder's machine, never in the hub, never in a log. Coworkers keep using the git and GitHub access of their own machine, as they do today.

**Intake route.** `POST /api/pr-review/comments`, JSON, written by the feeder's own token (new single scope `pr_review:write`, workspace-scoped, expires, revocable, one live token, the same rules as the pipeline token) or the signed-in workspace owner:

```
{"repo": "owner/name", "pr": 12, "head": "<40-hex sha>", "pr_state": "open", "fetched_at": "<ISO 8601>",
 "changed_files": ["path", ...],            // optional, for the head named above
 "comments": [{"kind": "inline|review|conversation", "id": "<GitHub id>", "thread": "<thread id or null>",
               "in_reply_to": "<id or null>", "path": "...", "line": 40, "commit": "<sha the comment was left on>",
               "author": {"login": "...", "type": "User|Bot", "association": "OWNER|MEMBER|COLLABORATOR|..."},
               "review_state": "COMMENTED|CHANGES_REQUESTED|APPROVED|null",
               "body": "...", "created_at": "...", "updated_at": "...", "removed": false}]}
-> 200 {"accepted": n, "duplicates": n, "edited": n, "unmapped": n}
```

A request is checked whole and stored in one transaction; one bad comment stores nothing. `400` for an unknown key or kind, a `repo` that is not `owner/name`, a `pr` that is not a whole number from 1, a SHA that is not full lowercase hex, a time that is not ISO 8601, more than 100 comments or more than 1 MiB in one request, a body longer than 65,536 characters (GitHub's own cap) or with control characters other than line breaks and tabs. `401` without a valid token, `403` for a connection that may not write, and the gateway refuses every other route to the feeder token. Comment text is stored exactly as sent (verbatim, no summary); it is not refused for looking like a secret, because the reviewer's words are the reviewer's, but every outward projection of it is redacted (see Privacy).

#### From a comment to a card to a Coworker

1. **Repository and PR to card.** The shared `cards_for` rules above. One visible card: the comment maps to it. No visible card: the comment is stored as `unmapped` with reason `no_card`; it shows on the Pipeline row of that PR ("3 review comments, no card") and maps by itself the moment a card's PR link matches (mapping is evaluated on read and on intake, never by guesswork on a PR number). More than one candidate: stored as `unmapped`, reason `ambiguous_card`, with the card numbers named so the owner can fix the link.
2. **Who may be heard.** A comment is work for the Coworker only when its author is trusted: the repository's `OWNER`, `MEMBER` or `COLLABORATOR` association, or a login the workspace has listed as a review agent. Anyone else's comment is stored with status `skipped` and reason `author_not_trusted`, is shown, creates no run and no Needs me item. Comments written by the Coworker itself (its logins, and its replies, which carry a hidden marker with the comment id they answer) are stored as `skipped`, reason `own_reply`, so the loop cannot answer itself. A review whose body is only `Reviewed head: <sha>` and `Verdict: PASS|CHANGES` (the public form of a gate verdict) is stored as a verdict line on the PR, not as work: its findings stay private, and a `CHANGES` verdict is handled by the failing-check rule, not by this loop.
3. **Owning Coworker.** The card's holder (`assignee`) while it holds the card, else the claimer of its last `doing` period; and the machine, project and topic of the card's last start job. A card with no such job, a machine that is revoked or not attested, or a board without an accepted Coworker config gets status `needs you` with a reason (`no_coworker`, `no_coworker_config`) and the one-click "Start Coworker" the Runs section already offers; the loop never invents a machine. A PR from a fork (the PR's head repository differs from the card's repository) is never worked: `fork_pr`.
4. **Branch it may touch.** The card's `branch` must equal the PR's head branch in the same repository, else `branch_not_owned`. The Coworker works in that branch only.
5. **Trigger.** One new source in the existing todo-trigger sweep: a card with comments in status `new`, a loop that is switched on for its board, rounds left, no live job, and a settled head (the card's `checks` is not `pending` for the current head; after 60 minutes of pending the run starts anyway) is started through the same fenced start, the same caps and the same bounded retries as a todo start. Comments that arrive while a run is live wait as `new` and join the next run: one run handles every waiting comment on the PR, in thread order, and at most 25 comments per run (more become the next round's work or, past the round limit, a Needs me item that says how many).

#### The loop, one round

1. The trigger starts the Coworker with the card's context and a new budgeted section, "Review comments", with each waiting comment quoted whole (JSON-quoted, as other card text is, never cut inside an item; an item that does not fit is left out with a `[cut: ...]` line naming the call that returns it). The comments are marked `working` with the job id and a round number. A run that is not renewed for 30 minutes returns its comments to `new` (the job lease already expires this way), and an attempt count stops a comment that keeps failing from looping.
2. **Comment text is data, not instructions.** It is quoted input from a person or an agent the owner trusts only as far as the code change it asks for. The Coworker's role text says so and the loop's tools do not offer anything a comment could ask for beyond the three outcomes below. A comment that asks for a merge, a rule change, a secret or access is answered `answered` with the reason, never obeyed.
3. For each comment the Coworker reports exactly one outcome with `pr_review_report`: **fixed** (a commit on the PR branch, named by its full SHA), **answered** (a reply that gives the reason it did not change the code, or the question it needs the reviewer to answer), or **needs you** (what only a person can decide, with the reason). Several comments may share one commit. The Coworker posts its reply on the PR through its own machine's access (a short plain reply, redacted, ending with the hidden marker), and the report carries the reply text so the card shows it without a GitHub call.
4. It pushes one normal commit (never a force push) to the PR branch, then reports the new head as it does today (`pr_head`, which clears `checks`). **One gate per head:** the existing review flow gates the new head once. The loop does not run a gate, does not re-run one on the same head, and does not post a second request for the same finding. If that gate returns changes the failing-check rule applies; it does not start a review round by itself.
5. The report is checked by the hub: the comment must be `working` under this job and this revision (a comment edited meanwhile is refused with `comment_changed` and goes back to `new` as the new revision); the commit must be the PR's head or an ancestor of it as the feeder last saw it, else the comment stays `working` and becomes `needs you` with `commit_not_found` after one feeder cycle; the changed files of the new head, when the feeder sent them, must not touch the protected path list (CI definitions, the merge-gate and review rule files, `CLAUDE.md`, coverage and lint settings, and removals or edits of test files that were not asked for), else the fix is held as `needs you` with `touches_checks`. A fix that would make a check pass by changing the check is a person's call.
6. **Counting.** A round is a run that handled at least one comment. The limit is two rounds per PR (workspace setting 1 to 3). After the second round, a third batch of comments (or comments still open after the second) becomes one `needs you` item for the PR (`rounds_exhausted`) and no new run starts. A failing gate on the fix head does not add a round here, but the failing-check rule's own three-round limit still applies and its stop also ends this loop for the PR. The counter resets only by a person's answer ("Two more rounds") or when the PR merges or closes.
7. When every comment on the PR is `addressed`, `answered`, `skipped` or `needs you`, the loop is quiet. A reviewer's reply on a thread is a new comment (its own id, `in_reply_to` the old one) and starts at `new`; the earlier comment keeps its status.

#### What the Coworker may not do

Enforced in the tools and the hub where the hub can see it, detected and surfaced where only the machine can act:

- **Merge.** No loop tool merges, closes, reopens or marks ready. Merging stays the person's own browser action with their own consent. A `pr_state` of `merged` arriving without a person's merge on the card is shown on the card as "merged on GitHub" and stops the loop; it is not an error the Coworker can cause through these tools.
- **Loosen checks.** The protected path rule above; a changed CI, gate, lint, coverage or rules file is held for a person. The loop never edits `checks`, never reports a check as passed, and never asks for a gate to be skipped.
- **Resolve a thread it did not fix.** The loop has no resolve tool in slice 2. An owner setting "Let the Coworker resolve threads it fixed" (off by default) may add it later: only for a thread whose comment is `addressed` with a commit, whose author is not a person who requested changes in a review that is still open, and never a thread with an unanswered reply.
- **Dismiss a human review.** No tool dismisses or approves a review. A review in `CHANGES_REQUESTED` is shown as such until the reviewer changes it on GitHub.
- **Push to a branch it does not own.** Only the card's branch in the card's repository, as a normal commit. The feeder reports the new head; a head that is not a descendant of the old head (a force push) or a head whose branch is not the card's is shown as `needs you` with `force_push_detected` or `branch_not_owned`. The hub cannot stop a machine from pushing. Branch protection on GitHub is the wall, and the setup guide says so: protected default branch, required reviews, no force pushes.
- **Act on a card it does not hold.** The report tool refuses a Coworker that is not the job's holder and a card the caller cannot see (the same uniform 404).

#### Idempotency: a comment is handled once

- **Key.** `(repository, PR, kind, GitHub comment id)` is unique. The edit time (`updated_at`; for a review body, which has none, its submit time plus a digest of the body) makes the revision: `(id, edit time)` already stored is a no-op that counts as a duplicate.
- **Edited.** A new edit time with a changed body digest makes revision N+1 and puts the comment back to `new` (the old reply and commit stay in its history). A new edit time with the same body (a reaction or a bookkeeping change on GitHub) is recorded as seen and changes nothing. A comment removed on GitHub becomes `skipped`, reason `removed_by_reviewer`, unless a fix is already linked.
- **Handled once.** Status moves forward only through the report tool or the sweep: `new` to `working` to `addressed`, `answered` or `needs you`. A repeated intake, a repeated report (same comment, job and outcome) and a resumed run are no-ops that answer the stored state. Two Coworkers cannot hold one comment: the `working` row carries the job id and the transition is one conditional update.
- **Feeder retries.** Intake is safe to repeat; the feeder may re-send a whole PR after a crash.

#### Status per comment, in one vocabulary

| Status | Plain words in the Deck | Meaning |
| --- | --- | --- |
| `new` | New | Stored, not in a run yet |
| `working` | The Coworker is working on it | In a live run (job, round, since when) |
| `addressed` | Fixed in `abc1234` | A commit on the PR branch answers it; the short SHA links to the commit |
| `answered` | Answered | The Coworker replied with a reason or a question; the thread waits for the reviewer |
| `needs you` | Needs you: the reason | A person has to decide or act; one Needs me item per card carries all of them |
| `skipped` | Not for the Coworker: the reason | Shown for completeness; never counted as waiting (author not trusted, own reply, removed, bot noise) |

`skipped` is a sixth word beside the five the card names, so that nothing the reviewer wrote disappears and nothing counts as work that is not. Each comment also keeps `reason` (a fixed code), `reason_text` and `next` (one sentence on what a person can do), `round`, `job`, `commit`, `reply` and the times. Every transition appends a row to the PR's own append-only history (who, when, from, to, reason); nothing is edited or deleted by the API.

#### How a person sees it

- **On the card.** A "Review comments" section in the card detail (a mount like Runs), beside the PR link: a one-line summary ("5 comments: 3 fixed, 1 answered, 1 needs you"), then one row per comment (author, file and line, the comment's text with a "Show more", the status in words, the linked commit, the Coworker's reply, and "Open on GitHub"). Text is the redacted view; "Show original" shows the stored words to a person who can open the card. A loading state, an empty state ("No review comments yet. They appear here when someone comments on the PR."), and a failed state with the reason and a Retry. The card row and the Board show a small count chip while anything is `new`, `working` or `needs you`.
- **On the PR.** The Pipeline PR row shows the same counts and a block "Review comments" between check and merge, with the run's time and duration like any other block.
- **Needs me.** Exactly one item per PR, raised by the loop through the card's ordinary ask: "Review comments on PR #12 need a decision: 2 of 5". The options: "Let the Coworker try again" (two more rounds), "I'll handle these myself" (the loop stops for this PR, comments stay visible), "Dismiss these" (they become `skipped`, reason `dismissed_by_person`, with the person's name in the history). The item names every comment still waiting and why; it does not paste comment text into the queue.
- **History.** Plain `comment` lines on the card without comment text: "3 review comments arrived (2 from a person, 1 from a review agent)", "The Coworker started round 1 on 3 comments", "Round 1: 2 fixed in abc1234, 1 answered", "Review rounds used up: 1 comment needs you".
- **Phone.** The same section, rows stacked, status word first, no horizontal scroll; the Needs me item is one tap to the section.

#### Resources and rate limits

Fixed in code, shown in the API and in the Deck text; hitting one is a visible state, never a silent drop.

- Intake: at most 100 comments or 1 MiB per request, 60 requests per feeder per minute, 2,000 stored comments per PR, 200,000 per workspace. Past a limit intake answers `429` with the reason and nothing is evicted.
- Runs: at most one live run per card (the existing one-active-job rule), at most 2 comment runs started per PR per hour, at most 3 comment runs live in a workspace at once, and every start counts against the machine's own hourly cap and low-memory refusal, which already produce `launch_reason` texts.
- Per run: at most 25 comments, and a context budget like other card context (`COMMONPLACE_START_CONTEXT_TOKENS`).
- Feeder: conditional requests, a 2 and 10 minute cadence, a pause when GitHub reports its own rate limit is near (the feeder reads the limit headers and says `feed_rate_limited` in its next post).

#### When it fails: every state has a reason and a next step

| Reason (`code`) | Plain text | Next step |
| --- | --- | --- |
| `feed_stale` | Comments may be missing: nothing was read from GitHub for 12 minutes. | Check that the comment reader is running (Settings > Review comments shows its last post), or press Check now. |
| `feed_rate_limited` | GitHub's rate limit is near; reading is paused until the reset time. | Nothing to do; it resumes by itself. |
| `no_card` / `ambiguous_card` | These comments are not linked to one card. | Put the PR's link on the right card. |
| `no_coworker` / `no_coworker_config` | No Coworker is set up to take this card. | Start a Coworker on the card, or set one up for the board. |
| `machine_unavailable` | The machine that ran this card is offline or switched off. | Bring it back, or start the card on another machine. |
| `start_refused` | The start was refused: the machine's reason, in the Runs words. | Follow that reason; the loop retries transient refusals a bounded number of times, then asks. |
| `run_failed` / `run_lost` | The run ended without reporting every comment. | Comments return to new once; after the second time they ask a person. |
| `commit_not_found` | The Coworker named a commit that is not on the PR. | Look at the branch; retry or handle it yourself. |
| `touches_checks` | The fix changes the checks or rules that judge the PR. | Read the change; accept it or ask for another. |
| `force_push_detected` / `branch_not_owned` / `fork_pr` | The branch changed in a way the loop does not do, or is not the card's. | Look at the branch on GitHub. |
| `head_moved` | Someone pushed to the PR while the Coworker worked; the fix cannot be placed. | Retry on the new head, or handle it yourself. |
| `reply_not_posted` | The fix is pushed but the reply did not reach GitHub. | Post the reply yourself; the text is on the card. |
| `comment_changed` | The reviewer edited the comment during the run; it will be handled again. | Nothing; it runs in the next round. |
| `rounds_exhausted` | Two review rounds are used up and comments remain. | Choose: two more rounds, handle yourself, or dismiss. |
| `author_not_trusted` | Written by someone the workspace does not act on. | Add them as a trusted reviewer, or ignore. |
| `intake_limit` | The comment limit for this PR or workspace is reached. | Dismiss old comments; nothing was dropped. |

Every `needs you` reason is written on the Needs me item and on the comment; none shows "something went wrong". Failures are logged by code and counts only.

#### Privacy

Comment text never leaves the workspace through Commonplace: it is stored in the workspace's own file (`pr_review.sqlite3`, next to `pipeline.sqlite3`, so it is encrypted with the workspace, backed up with it and never mixed with another workspace), the hub makes no outbound call that carries it, outbound webhook payloads carry only ids, statuses and counts (the existing metadata allowlist), and nothing is sent to a model service the owner has not already configured for that Coworker. The Coworker reads the text because it is the Coworker's work, on the machine and with the model the owner chose for it. Logs record the repository, PR number, comment id, status, reason code and counts, never a body, a reply, a path's contents or a token; every outward projection (the Deck list, the history lines, the Needs me item, the Coworker's context, error texts) passes `redact` first, and the Coworker's reply is redacted before it is posted. The feeder's token is write-only to one route, workspace-scoped, shown once and stored only as a hash. Reads follow card visibility: a person who cannot open the card cannot read its comments, and an unknown, foreign or hidden card gets the same 404. Agent tokens use the tools, not the people routes (403).

#### Slice plan

Three pull requests against `develop`, each under 300,000 bytes of diff, each with its docs fragments and tests that fail on the base and pass on the head, and no full test suite.

**PR 1: server: intake store, mapping, statuses, REST and MCP, trigger.** New package `commonplace/pr_review/` (`store.py` tables `pr_review_prs`, `pr_review_comments`, `pr_review_events` in `pr_review.sqlite3`; `intake.py` validation and idempotent upsert; `mapping.py` card, owner, branch and trusted-author rules, with `cards_for` moved to a shared module and its pipeline tests unchanged; `status.py` the transitions and reasons; `routes.py` intake, list, watch, decision; `tools.py` `pr_review_list` and `pr_review_report`; the trigger source in `orch/triggers.py` with the card ask for `needs you`). New scope `pr_review:write` in `policy.SCOPES` and the gateway's single-scope rule, route inventory entries, account export and deletion entries, board setting for the loop (off by default). The workspace owner's own workspace turns it on after slice 2 proves itself.
Acceptance: a comment posted to intake for a PR with one visible card is stored once, repeating the request changes nothing, an edit with a changed body makes revision 2 and `new` again, an edit with the same body changes nothing; a comment with no card or two cards is `unmapped` with its reason and maps once the card link is fixed; an untrusted author is `skipped`; the Coworker's own reply is `skipped`; a start is requested exactly once for waiting comments, not while a job is live, not past two rounds, not for a fork PR; the report tool refuses another Coworker, a stale revision and a commit the feeder did not see; every refusal in the failure table that slice 1 can produce has its code and text; the feeder token reaches only the intake and watch routes; a person without card access and another workspace get the same 404; no log line or error contains a comment body or token (tested with a secret-looking body); the pipeline card-lookup tests pass unchanged. Tests: the new files fail with an import error on the base; module and system docs updated.

#### Open questions (answers the project owner has to give), and what is decided by default

Needs the project owner:

1. **The feeder's GitHub credential.** Default: a fine-grained, read-only token (pull requests and contents: read) for the watched repositories, held on the production host or one runner machine, never on the hub, created by the owner. Nothing is built that needs more; the first poll waits for this credential.
2. **First switch-on of public replies.** Coworker replies and fix commits on a public repository are visible to everyone. Default: the loop is off per board until the owner turns it on, the first run on a public repository is a dry run that shows the proposed replies on the card before posting, and a repository's trusted reviewers are listed by the owner.

Decided here, change if you disagree:

3. **Fix rounds.** Two per PR (workspace setting 1 to 3). The project's three-round rule for failing checks stays separate.
4. **Thread resolution.** The Coworker does not resolve threads in slice 2; the optional setting comes later.
5. **No inbound webhook.** The feeder is the only reader of GitHub.
6. **Skipped is a sixth status** so nothing a reviewer wrote disappears.
7. **Stored verbatim, shown redacted.** The original stays one click away for people who can open the card.
8. **Only boards with a Coworker config start runs by themselves;** other boards get the Needs me item with the Start Coworker button.
9. **Comments without a card are kept, not dropped,** and map by themselves later.

#### Slice 1 as built (card #613, PR 1): how it differs from the plan

The slice follows the plan above. These are the places where building it settled a detail; the plan's text stays as the intent.

- **Code.** `commonplace/pr_review/` (`intake`, `store`, `status`, `mapping`, `trigger`, `needs_me`, `routes`, `tools`); tests `tests/test_pr_review.py`. The comments live in the workspace file `pr_review.sqlite3` next to `pipeline.sqlite3`. The pipeline's card choice is reused through `pipeline.cards.pick_with_reason`, not copied.
- **Intake body.** In addition to the fields above, a request carries `branch` and `head_repo` (the PR's head branch and repository, for the fork and branch rules) and an optional `changed_files` list for the head it names (for the protected-path rule). The PR's `head` and `pr_state` are stored with each request.
- **Feeder token.** The scope `pr_review:write` is minted like the pipeline token (`commonplace token add review-feed --workspace <workspace> --client feeder --scopes pr_review:write --by <owner email>`), alone, for an owner, at most one live. The gateway lets it call `POST /api/pr-review/comments` and `GET /api/pr-review/watch` and nothing else. The watch answer is `{"prs": [{"repo", "pr", "card"}]}` for the open PRs of cards on boards where the loop is on; the `check_now` flag comes with the Deck slice.
- **Owning Coworker and machine.** A start is not aimed at a machine by this slice: on a board with an accepted Coworker setup the ordinary todo trigger starts the Coworker from that setup's machine, project and topic. The loop only hands the card back. The card's last start job is not read.
- **The trigger.** A finished card waiting in a completion review is handed back for more work (`decide`, "Return for more work") as the person who switched the loop on for the board; that person's switch is the delegation, and it is on the card's history line. The return fires the existing todo trigger, so no second way to start work exists. A card in `todo` or `doing` is left alone (the comments wait and the Coworker takes them with `pr_review_take`); a card waiting for a person's own answer (a Coworker question, a plan) keeps its comments waiting. The trigger runs after every runner sweep and after every intake or "try again" answer.
- **Rounds.** A Coworker takes a round with `pr_review_take` (its own tool and a checked write; `pr_review_list` only reads) while it holds the card (at most 25 comments, in thread order). A round whose run reports nothing and whose comments return to `new` is given back, so a lost run does not use up a round.
- **Fix confirmation.** A report of a fix names a full commit; it is `addressed` when that commit is the PR head the feeder last saw, `working` (pending) until then, and `needs you` with `commit_not_found` when the feeder has read the PR again 10 minutes later and still does not see it. Whether the commit is an ancestor of the head is not checked: the feeder does not send history. The protected-path rule needs the changed files of that same head: a head that arrives without a file list makes the list unknown (an earlier head's list is never reused), the fix stays pending, and after the same grace it asks a person (`files_unknown`). One trigger pass looks at 20 PRs at most, longest-waiting first, so a burst of intake cannot make one request do unbounded work.
- **The one question.** `pr_review_report` places the question as the Coworker; the trigger places it as the person who switched the loop on. A card that already has an open question keeps it. The person's answer arrives at `POST /api/pr-review/cards/<n>/decision` (`again`, `mine`, `dismiss`); answering the card's question through the generic answer path does not change the comments yet, which is part of the Deck slice.
- **Not in this slice.** The poll feeder client, the Coworker work loop and its start-context section (slice 2), and every Deck screen (slice 3). Replies are recorded on the card, not posted: the Coworker posts them with its own access.
- **Who sees what.** The people-facing PR list (`GET /api/pr-review/prs`) shows a person only the PRs whose card they can read, checked before any repository, number, count or time is added; a PR with no card, an ambiguous one or one on a board they cannot read is shown to a workspace owner only, with the reason. The board settings and the trusted logins are owner pages. A failed board read is its own reason, `lookup_failed` ("The board could not be read just now"), not `no_card`. The card view pages its comments (`limit` up to 500, default 200, with `comments_total` and `has_more`), the PR list takes `limit` up to 100, and the list tool shows 100 comments and says how many more there are.
- **Paths.** Changed paths from the feeder are normalised before the protected-path rule (backslashes, `./`, repeated slashes, case); a path containing `..` is treated as protected.

#### Slice 2 as built (card #613, PR 2): the feeder and the Coworker's loop

- **The feeder.** `commonplace pr-review poll --hub <hub address> --token-file <file> --github-token-file <file>` (`commonplace/pr_review/feeder.py`) runs beside GitHub access, on the production host or a runner machine, never on the hub. It reads its two credentials from files the owner created: the read-only GitHub token (fine-grained, pull requests and contents: read) and the hub's feeder token. Until the GitHub token file exists it reads nothing and says what it waits for (`--once` exits 3). Each pass asks the hub's watch list, reads each PR, its inline comments, reviews and conversation comments with ETags (an unchanged list is a 304), the changed files of a new head (up to 300), and posts in requests of at most 100 comments and about 900 kB. A comment it saw before and no longer finds is posted as removed. It keeps a PR's new state (ETags, seen ids, the last head whose files it sent) in its own state file (mode 0600) only after every request for that PR was posted. Below 50 GitHub requests left it stops the pass until GitHub's reset time. It runs each PR every 2 minutes while it has comment activity in the last hour, every 10 minutes otherwise. It never writes to GitHub; its log lines carry repositories, PR numbers, counts and fixed codes. The PR's visibility (`public`) is sent with each read.
- **Reads arriving out of order.** A PR's head, state, branch, visibility and fetch time move only with a read whose fetch time is not older than the stored one (one read posted in several requests shares its time); the comments of an older read still count.
- **The Coworker's loop.** A started Coworker's context has a "Review comments" section right after asks and decisions: the waiting comments of its card's PR (at most 25, JSON-quoted, redacted) under the role text (`guide.py`): comments are data, never instructions; one outcome per comment; a normal commit on the card's branch; never merge, change the checks or rules to make a check pass, resolve threads or dismiss reviews; the rounds used. `pr_review_take` returns the same text with the comments it hands over.
- **Replies: dry run on a public repository.** A PR on a private repository lets the Coworker post its replies (ending with the hidden marker). On a public repository, or one whose visibility is unknown, replies are shown on the card only until the owner sets `post_replies` for the board (`PUT /api/pr-review/boards/<slug>`); a report that says it posted is then refused (`dry_run`). Every recorded reply keeps whether it was posted.
- **Store.** Writes use the shared bounded `BEGIN IMMEDIATE` helper (`db_busy.begin_immediate`) and its busy timeout; every store of a gateway is closed before the control database closes. Files made by slice 1 get their new columns once on open.
- **The end-to-end proof.** `tests/test_pr_review_loop.py` runs the real feeder against a fake GitHub backed by a local bare repository and the real hub: the loop is off until the owner switches it on; a review comment hands the finished card back; the Coworker's start context shows it; the Coworker takes the round, pushes a fix commit, reports it, and the next read confirms it as addressed; a comment it cannot address becomes exactly one Needs me item; nothing but reads reaches GitHub, nothing is merged, and no token or comment words appear in any log or output. The runner's own start of the Coworker is the existing todo trigger and is not repeated in this test: there, the board counts as having a Coworker setup.

#### Follow-up (card #629): bad input and report batches

- The feeder treats a malformed answer as a fixed code instead of an error that stops it: a watch answer that is not JSON or has no list of PRs stops the pass (`hub_bad_answer`); a GitHub answer that is not the expected object or list of objects skips that PR (`github_bad_answer`), and nothing of that read is kept, so the next pass reads it again; a watch entry without a repository name and a whole PR number is left out. Any other error skips only its PR and is logged by its type, never its message; the polling loop goes on after a bad pass.
- `pr_review_report` checks every report of a call (fields, the dry-run rule, that each comment belongs to the card's PR, the outcome's required commit, reply or note) before it stores any, and stores them in one transaction; a refusal says that nothing was stored. This must be in place before the loop is switched on for a board.

#### Slice 3 as built (card #613, PR 3): the Deck

- **On the card.** A card with a pull request has a "Review comments" section between Runs and Previews, in both the Deck and the Classic look. It says how many comments there are and what became of them ("6 comments: 1 fixed, 1 answered, 1 need you, ..."), the round counter ("Round 1 of 2 used", and that new comments wait for the owner once no rounds are left), and how replies reach GitHub (posted, or shown here first on a public repository). Each comment shows its status in the server's words, who wrote it and where, its words (long ones fold with "Show all of it"; words that looked like a password or key are hidden until a person who can open the card asks for the original), the fix commit as a link (and that GitHub has not shown it yet, when that is so), the Coworker's reply ("Reply on GitHub" or "Proposed reply (not posted)"), its note, and for a comment that waits or was set aside, the reason and the next step. While the Coworker works the section reloads itself every 5 seconds, keeping focus on the same control.
- **The three answers.** When comments need a person, the owner sees "Two more rounds" (or one or three, after the project's rounds), "I will do it myself" and "Ignore", each with one sentence on what it does. The answer also answers the card's own question, so the Needs me item goes: back to the Coworker for another round, to Backlog for "I will do it myself" (so no Coworker picks the card up), or back to the Coworker with the comments set aside for "Ignore". The same answers given on the card's question elsewhere (Needs me) reach the comments on the next trigger pass, once. A member reads everything and is told a workspace owner decides.
- **Project settings > Review comments (owner).** The switch (off by default), rounds before it asks (1 to 3), posting replies on public repositories (off: replies are shown on the card first; private repositories are always posted), the people the Coworker listens to (repository owners, members and collaborators already count; others can be added, and the Coworker's own account so it never answers itself), and the comment reader's status: waiting for the owner's token, waiting for its first read, working (with the last read), or late. A member does not see the section. When the switch is off, the card's section tells the owner where to switch it on and links there.
- **Pipeline.** A pull request with review comments shows one chip ("2 review comments need you", "1 review comment is being answered", "3 review comments, all handled") and a link to the card.
- **Proof.** `tests/cardreviews.mjs` (28 cases through `tests/test_card_reviews_ui.py`) and `tests/test_card_reviews_browser.py` (every state for owner and member, Deck and Classic, at 1280, 390, 320 and 768 touch; the answer flow with focus after the action and after a background reload; the settings; the Pipeline chip). Captures are kept with the review evidence, named by commit.
