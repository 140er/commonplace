### Shared team bots

- `docs/design/shared-team-bots.md` is the design note for sharing a bot with workspace members (card #462). Decisions it proposes: a shared bot acts with the intersection of the bot's owner-set access, the talking member's rights and the owner's rights; private threads stay private to their person; sharing is off by default per workspace and a new share reaches nothing until the owner grants it. No code changed; slices follow one PR each.

- Slice S1 (store foundation, no routes or tools): the tables, the upgrade of an old `bots.sqlite3`, `BotStore.reach`, store-level share, revoke and access edits, and the control-side `bot_sharing_settings` switch (off by default) exist and are unused. Decisions taken from the note's recommendations: a per-workspace switch the workspace owner turns on and any member may then share their own custom bots (question 1); a member's own notes live apart from bot-level notes (question 4). Membership checks stay with the caller (a route in a later slice); the store checks the share, the switch and the thread.

- Slice S2 (effective access and enforcement): a shared bot's turn reaches `bot access ∩ talker ∩ owner` from fresh principals on every call; every tool declares a `reach` and `register` refuses one without it. Decisions taken where the note was open: a `tool` entry is always required for a tool with a reach other than `none` (default deny, so the board seed alone lets the bot read its project into the prompt but call no project tool until the owner names tools); starting or cancelling an agent needs a project `write` grant as well as a machine grant; `create_project` is `wing:write` and so never offered to a shared bot until wing grants exist; a model may name any project the asker reads, so a project outside the bot's reach gets the clear `outside_bot_access` sentence instead of a schema error; a grant is checked against the owner's rights only when it is new or its mode changes, so an owner who lost a project can still save the rest of the list (that entry stays dormant). The access routes are web session only for changes; reads are open to apps that act as a member with a live share.
