### Chat-platform bots (foundation, identity, intake, turns and confirmation built)

- `docs/design/chat-platform-bots.md` plans bots that people reach from a chat platform. A bot acts only as the linked person, in a channel it is narrower than on the web, every write needs the person's confirmation, and everything is off until the workspace owner installs and enables it.
- Slice 1 (card #455) is in: the workspace file `chat_bridge.sqlite3` (created only by the first install), sealed credentials (write-only, never in a response, log, audit row or tool result), the owner install routes under `/api/bridge/installs`, a credential test through the adapter interface that an install needs before it can be enabled, one install per platform team on a hub, the read-only `bridge_status` tool and the `commonplace bridge status|disable` kill switch.
- Slice 2 (card #455) is in: a signed-in member asks `POST /api/bridge/installs/<id>/link-code` for a code (shown once, 10 minutes, single use, stored only as a hash, five wrong tries lock a sender) and sends it to the app in a direct message; that binds the platform id to the person for that install (one person and one platform id per install). `GET /api/bridge/links` and `DELETE /api/bridge/links/<id>` are the person's own links (another person's is a 404); the owner sees who is linked and can end any link under `/api/bridge/installs/<id>/links`. Unlinking ends it at once, a code sent in a channel is burned, and every event re-checks that the install is on, the link is live and the person is still a member.
- Slice 3 (card #455) is in: the public intake `POST /api/bridge/in/<install>/events` verifies the platform's signature, ignores bots, edits and anything not addressed to the app, journals each event once (a platform retry runs nothing), looks up the link and runs the linked person's own Bots-layer turn: a direct message with their General bot, a mention in a channel the owner mapped (`PUT /api/bridge/installs/<id>/channels/<channel>`, `titles` by default) with their project bot for that project only, read-only and with no private context. The reply is queued in an outbox and posted once into the thread (or the DM); retries are bounded, a restart mid-turn ends as an interrupted reply that is not rerun, and an install that is off answers 404 and does nothing. No writes from the chat yet (they come with confirmation) and no real platform adapter yet, so creating an install answers `unsupported_platform` until one is registered. The code is `commonplace/chat_bridge/` (the name `bridge` was taken by the MCP client bridge).
- Slice 4 (card #455) is in: on a chat direct message nothing writes with the person's identity without their own tap. With `confirm_ok` off (the person's own switch, `PATCH /api/bridge/links/<id>`, default off) a writing tool is not offered at all and a confirm tool waits in the web app; with it on the writing tools become confirm tools, a private chip with server-built text goes to the asker, and only that person's signed tap (right platform id, right place, live link, still a member, install on) runs the stored action, once; late, repeated and foreign taps get one fixed sentence and run nothing. Starting an agent, approving and creating a project stay web-only unless the owner allows them per install (`consequential_taps`). A channel turn is still read-only and never gets a chip.
