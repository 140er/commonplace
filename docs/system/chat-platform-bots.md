### Chat-platform bots (foundation and identity built)

- `docs/design/chat-platform-bots.md` plans bots that people reach from a chat platform. A bot acts only as the linked person, in a channel it is narrower than on the web, every write needs the person's confirmation, and everything is off until the workspace owner installs and enables it.
- Slice 1 (card #455) is in: the workspace file `chat_bridge.sqlite3` (created only by the first install), sealed credentials (write-only, never in a response, log, audit row or tool result), the owner install routes under `/api/bridge/installs`, a credential test through the adapter interface that an install needs before it can be enabled, one install per platform team on a hub, the read-only `bridge_status` tool and the `commonplace bridge status|disable` kill switch.
- Slice 2 (card #455) is in: a signed-in member asks `POST /api/bridge/installs/<id>/link-code` for a code (shown once, 10 minutes, single use, stored only as a hash, five wrong tries lock a sender) and sends it to the app in a direct message; that binds the platform id to the person for that install (one person and one platform id per install). `GET /api/bridge/links` and `DELETE /api/bridge/links/<id>` are the person's own links (another person's is a 404); the owner sees who is linked and can end any link under `/api/bridge/installs/<id>/links`. Unlinking ends it at once, a code sent in a channel is burned, and every event re-checks that the install is on, the link is live and the person is still a member.
- No platform adapter, intake or turn exists yet: the public intake paths answer 404, and creating an install answers `unsupported_platform` until an adapter is registered. The code is `commonplace/chat_bridge/` (the name `bridge` was taken by the MCP client bridge).
