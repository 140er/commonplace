### A search never waits on the index job for more than a bound

Production, right after a deploy and its backup (14 Nov 2026): four searches in a row waited out their 60 s client limit, the fifth took 18 s, then everything was normal; the gateway log showed `startup context unavailable (TimeoutError)` and a search-index job running at the same time. The startup-context step was not the cause: it runs only on `initialize`, has its own 80 ms deadline and a failure only drops the optional context, so its log line was the bound doing its work on a slow host.

Root cause: a person's palace read and the index backfill's write share the worker's request lock, and that lock was writer-preferring with no bound on a reader's wait. A write that held the lock, or only waited for it behind one slow search, kept every later search out; the gateway then waited for the worker for up to 11 minutes (its transport limit), so each search stood for as long as the write and the searches before it. The index job's own pacing (small steps, rest after a write, a pause while people search) lowers how often that happens but cannot bound a search that is already queued.

Decision: the worker now bounds the wait on its side. A palace read waits at most 5 s (`MEMPALACE_READ_LOCK_WAIT_S`) and then answers a retryable busy error (`-32001`, "Memory is busy indexing; try again in a moment"); the Memory route maps it to its normal retry message, not to an empty result. An index write takes the lock politely, so it never makes a reader wait for it: it enters only when no read runs or queues, waits at most 10 s (`MEMPALACE_MIRROR_LOCK_WAIT_S`) and otherwise answers the same retryable error without writing, and the job backs off as for any refused write. The same bounds hold where either side gives the lock up on purpose: between index units, and around embedding inference. A write that cannot take it back in time ends the batch with the retryable busy answer (units already written stay, nothing is written without the lock); a read that cannot take its lease back answers busy. The abort is a `BaseException` internal to the worker, so a broad `except Exception` in embedding or write code cannot swallow it. The gateway keeps the answer typed (`-32001`, `retryable`) for MCP clients and for its own calls. Units are idempotent, so a refused or interrupted batch is replayed whole. Typed association reads stay unbounded: a busy answer there would silently hide a hit from the proof, which is worse than waiting.

Not done here: the double proof of each hit and the workspace path stats are real costs but not the cause of a stall, and are left for their own card with a same-results test. Measured through the real route and a real worker (local harness, real embeddings): 160 searches during four 48-unit index batches took a median 0.03 s and at most 0.36 s before and 0.31 s after, with the batches taking the same time (8.2 to 11.8 s before, 8.1 to 11.7 s after); with the palace held for 8 s a search answered after 8.0 s before and, with the busy answer, after 5.0 s after, and the next search returned its hit in 0.04 s.
