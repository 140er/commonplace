### Compute: add a machine without SSH (guided pairing, slice 1)

A person adds a machine in the Compute section by choosing what kind of machine it is, copying one command, running it on the machine and accepting once in the app. The app shows the machine as it connects, shows every step's state, and says what to do next when a step fails. This note is the design; it was written before the code. Slice 1 is delivered as three stacked changes: **A** the server (pairing records, the approval state machine, the API, the code lifecycle), **B** the installer that the command runs, **C** the screens (Classic and Deck, phone included). Where this note says "not in this slice" the app says the same in plain words.

#### What exists today (gap analysis, develop at the start of this slice)

Runner machines (a runner runs Coworkers):

- `commonplace/runner/enrollment.py`, `enrollment_api.py`, `enrollment_crypto.py`: owner opt-in (`/api/runners/install-settings`), one-time enrollment code (256 random bits, five minutes, SHA-256 hash only, one consumer), uniform refusals, durable ten-per-minute counters, `exchange` that creates one disabled, unbound machine with separate machine and worker credentials sealed to the machine's RSA key, key-bound recovery of a lost response. Pinned by `tests/test_runner_enrollment.py`.
- `commonplace/runner/installer.py`, `install_cli.py`, `install_host.py`, `install_files.py`, `install_receipts.py`, `bootstrap.py`: the machine-side installer (`commonplace runner install`), setup-only user service, private 0700/0600 files, manifest, uninstall, signed bootstrap launcher. Pinned by `tests/test_runner_install*.py`.
- `commonplace/runner/setup_api.py`, `setup_approvals.py`, `device_login.py`, `runtime_status.py`, `lifecycle.py`: provider sign-in cards, fingerprint comparison, sealed host grants and machine-reported component facts (`agent_ready` is always false there: reports are facts, never authority). Pinned by `tests/test_runner_setup_*.py`.
- `commonplace/runner/registry.py`, `owner_api.py`, `requester_api.py`, `web/static/adminrunners.js`: the owner screen and API for machine grants (projects, topics, wings, requesters, runtime ceiling), attestation and revoke.
- Gate on running work: a machine runs a card start only when it is enabled **and** its binding is owner-attested (`runner_api.py`, `capacity.py`); an enrolled machine is inert until both.

Compute targets (an SSH-reachable machine that runs approved scripts): `commonplace/compute/target_installer.py` (root install, manifest, socket-activated SSH handled since the follow-up recorded in `docs/system/compute-installer-followup.md` and `docs/modules/compute.d/socket-activated-ssh.md`), `target_helper.py`, `script_sandbox.py`, `docs/compute/RUNNING.md`. Everything about enrolling a target is a proposal only (`docs/design/compute-target-one-click.md`): no code issuance, no signed package, no approval-key pin (`pin_approval_keys` still raises), no API.

What a person must do by hand today to add a runner:

1. Turn on setup with a raw `PUT /api/runners/install-settings` (there is no screen).
2. Work out a 64-hex "manifest digest" and hand-write the grant JSON (label, projects, topics, wings, mode ceiling, requesters), then `POST /api/runners/enrollments`.
3. Copy five values (hub address, workspace id, label, enrollment id, digest) into `commonplace runner install`, and pipe the code in on stdin.
4. Prepare the machine: Python, `cryptography`, a systemd user manager, linger, bubblewrap where scripts are used; on a stock Ubuntu 24.04 box nothing checks these before the code is spent.
5. Find the machine in Needs me, compare fingerprints, attest topics and provider, add every requester again (#452) and re-pick wings and topics (#452).

What is missing for "Add machine, pick kind, one command, appears as it connects, one accept, per-step states":

| Missing | Where it lands |
|---|---|
| A screen or API that creates an enrollment without hand-written JSON or a hand-computed digest | A (`pairing.create` derives the digest and the grant) |
| One string that carries every public value, so nothing is copied by hand | A (`setup` envelope) and B |
| "Same as machine X" copying projects, topics, wings, mode ceiling and requesters (#452) | A (`copy_from`), C (the choice) |
| Seeing the machine appear when it connects, and seeing a failed step | A (`state`, reported `steps`), C |
| A clear refusal for a stale, used or foreign code (the exchange refuses everything alike on purpose) | A (`/api/runner-pairing/check`, code and pairing id as authority) |
| One accept that shows machine identity and grants in words | A (`accept` with an identity digest), C (the sheet) |
| An installer that checks the machine before it spends the code, handles stock Ubuntu 24.04 and reports step results | B |
| Offline handling for an approved machine, revoke and re-enroll with the same values | A (`offline`, `close`, `retry`), C |
| A target (SSH script) enrollment | Not in slice 1 (see below) |

The loose cards: #490 (enroll from the app without a bot) is the whole of this slice for runners; #447 (stock Ubuntu socket-activated SSH) is already fixed in `target_installer.py` and B adds a fixture test for the runner installer's own prerequisites; #448/#449/#450 are the designs this slice builds the runner half of; #451 (no one-click path, runner box needs hand installs) is A+B+C; #452 (requesters) is `copy_from` and the carried `requesters` list; #430 (agentic first) is the rule: one command and one accept, no later prompt on the machine.

#### Decisions

**Machine kinds.** `runner` is available. `target` (script target over SSH) is listed and refused with the reason `kind_unavailable`: its design needs the owner's approval keys (#431/#509) and a signed package that do not exist, and a flow that cannot verify what it claims would be worse than none. The app shows the kind as "Not available yet" with that sentence.

**One pairing record.** `machine_pairings` (control database, next to `runner_enrollments`) links one owner request to one runner enrollment: id, workspace, kind, label, owner, `request_id` and a hash of the request, the enrollment id, `version`, the accept decision, closed reason, last report time. `machine_pairing_steps` holds the machine's latest report per step. The pairing grants nothing by itself: authority stays in `runner_enrollments`, `runner_machines` and the ordinary approvals. Creating a pairing issues the enrollment in the same transaction and audits both.

**Pairing code lifecycle.**
- Created by the signed-in owner of the workspace (a person session; agent tokens and members are refused with a reason). 256 random bits, valid 15 minutes (the legacy enrollment keeps five), stored only as a SHA-256 hash, returned once in the creation response, never again (not by `GET`, not by an idempotent replay, not in the audit row, not in logs). A lost command means "Set up again": a new code, the old one revoked.
- Single use: the exchange consumes it in one conditional update; a second try is refused, and the first machine's credentials are unaffected.
- Scoped: to the workspace, the kind (`runner`), the exact label, and a digest of the frozen intent (grant plus plan version) that the installer must echo back; changing any of them after issuing needs a new pairing.
- Rate limited: creating is capped per workspace and minute, and at five open pairings (`MAX_OPEN`); the check and exchange routes share the existing durable per-workspace counters; reports are capped separately.
- Refused clearly when it cannot work, to the holder of the code only: `POST /api/runner-pairing/check` takes the workspace, the pairing id and the code (no cookie, no bearer token) and answers `usable`, or one of `expired`, `used`, `cancelled`, `revoked`, `setup_off`, `not_for_this_workspace`, `code_mismatch`, each with a plain sentence and a next step. The exchange itself keeps its uniform refusal, so a guess learns nothing; the pairing id is not a secret but is useless without the code, and it answers the same `code_mismatch` for a wrong code and an unknown id.
- Expiry is checked at every use; the existing sweeper persists it. An expired pairing is shown as "Code expired" with "Set up again".

**What the installer does and verifies (change B, delivered).** The command is ` S=$(curl -fsS '<hub>/machine-setup.sh') && printf '%s' '<code>' | sh -c "$S" machine-setup '<envelope>'`: the launcher is fetched first and the rest runs only if that worked, so a failed download stops with curl's own message instead of running an empty script. The hub address is https, or plain http only to the machine itself. `GET /machine-setup.sh` is public and the same text for every caller (a small shell launcher with `commonplace/runner/machine_setup.py` embedded; it holds no secret and no tenant data). The code arrives on standard input, never as an argument; the envelope has public values only. The launcher finds Python 3.10 or later (if there is none it reports `missing_python` itself) and runs the embedded, standard-library-only program under `python3 -I`. The program, in this order:

1. Reads the envelope and the code and refuses a broken command (exit 2, nothing asked of anyone).
2. Checks the machine, read-only, in a fixed order, each failure with a cause the app already has: not root (`run_as_root`), Ubuntu 24.04 or later or Debian 12 or later (`unsupported_os`), Python (`missing_python`), the `cryptography` package (`missing_prerequisite`), the runner program (`missing_runner_program`), a running user service manager (`no_service_manager`), 256 MB free (`disk_full`). It never touches SSH or the system's service configuration, so socket-activated SSH on stock Ubuntu 24.04 is simply not involved.
3. Reports the result to `POST /api/runner-pairing/check` (code and pairing id as the credential), which also answers whether the code can still work. A failed check is shown in the app with its cause and **the code is not spent**; the one next step, on the machine and in the app, is to open Compute in the app and choose Set up again (the app cannot reissue the old command, so it never points at it). A code that ran out unused reads `expired` for the owner and for the machine whatever a check reported before. An unusable code is explained in the app's own words (used, expired, cancelled, wrong workspace).
4. If the machine does not already keep user services running after logout, asks for one administrator confirmation (`sudo loginctl enable-linger`, the system's own password prompt); a refusal is reported as `missing_privilege`. This is the one accept on the machine, and only on machines where it is needed.
5. Runs the existing installer, which spends the code, writes the private installation (0700/0600) and the setup-only user service, then reports `files`, `service` and `check` with the machine's own credential. A failure is reported as the step it reached: `files` before the code is spent (the code stays usable; the check route accepts a `files` report only while the code is live) or with the machine's own credential after it, `service` once the private files are written, `check` after install. When the code was spent and nothing could be saved the machine holds no credential, so nothing can be reported: the machine says so, the page stays at Machine connected with Approve unavailable, and after 15 minutes without all four steps it reads **stalled** ("This setup has not finished. Remove this machine and set it up again.", with Set up again offered). The window says exactly that ("After 15 minutes Compute shows this setup as not finished; then open Compute in the app and choose Set up again."), not an immediate Set up again. A refused exchange is not a lost connection: the machine asks the site why and prints its answer (used, expired, cancelled). Running the same command on a machine that holds a private installation for the same enrollment continues it; one for a different enrollment on the same site (the first try, cancelled by Set up again) is removed first by the installer's own uninstall, so choosing Set up again always works. One made for a different site is never touched and its credential is never sent here: the command prints that site and "Nothing was changed."
6. Prints the machine key fingerprint in the same eight-character groups the app shows, before it reports the last steps, so it is on the screen when the app can first show the machine as finished, and says to return to the app.

What this change does not do, and the app says so: it does not deliver the runner program (a signed release channel is a separate piece; step 2 checks it is installed and says so when it is not), the setup-only service sends no heartbeat, so a machine never reads Offline until it has sent one (silence proves nothing; the page shows when it was last seen), and trust in the launcher is the hub's HTTPS origin, the same origin that issued the command. Tests use a fake probe, a recording user manager, the real pairing handlers behind in-memory streams, stub programs for the shell launcher and a real in-process hub; no real host, no real user manager and no network.

**Requester carry-over.** The grant frozen at creation includes `requesters`. `copy_from` copies projects, topics, wings, runtime ceiling, in-flight and hourly limits and requesters from an existing active machine of the same workspace; each value is validated again against the current owner (a requester must still be an active trusted workspace agent), so nothing is inherited from a revoked or lapsed source. Explicit fields override the copy. Nothing is copied that is a credential, a provider sign-in or an attestation.

**What the owner approves (the one accept).** When the machine has connected, the owner sees in plain words: the machine's label, its key fingerprint (short groups to compare with what the command printed), what it may read (wings, projects, topics), who may start work on it (requesters), the runtime ceiling and limits. Accepting posts the pairing `version` and the **identity digest** the screen showed; if the grant or the machine key changed in between, the answer is `identity_changed` and the screen reloads. **The server refuses an accept until all four steps are `ok` and the setup is not stalled** (`not_finished`, `stalled`): the machine prints its fingerprint only as it finishes, so an approval before that would compare with nothing. The page greys Approve out for the same reason, but the authority is the server's. The accept enables the machine and records who approved what and when. It does not attest the binding and it does not sign in a provider: a machine runs Coworkers only when it is enabled **and** attested (unchanged), so "Approved" and "Ready" never claim that work runs. Approval is an ordinary signed-in owner decision; independent owner keys (passkeys) are not in this slice and the app says so.

**States** (one list, derived by the server, one sentence and one next step each): `waiting` (Waiting for the machine), `connected` (Machine connected, waiting for your approval), `approved` (Approved: finishing setup on the machine; since the four-step rule only a record approved before it can sit here), `ready` (Set up and checked), `offline` (nothing heard for over 15 minutes), `failed` (a step failed, with its cause), `expired`, `cancelled`, `declined` (only the owner's own "This is not my machine" on a healthy connected machine), `abandoned` (a failed or stalled setup that the owner removed or set up again: "Setup removed", never a decline), `revoked`. `ready` means: approved and all four steps reported `ok` (it stays `ready` until a heartbeat, which the setup-only service does not send, is older than 15 minutes). A stalled setup (connected and unfinished after 15 minutes) keeps its state but is labelled "Not finished" for owner and member. It deliberately does not mean "Coworkers can run here"; the view carries `binding_state` so a screen can say that the provider connection and attestation still come next, on the screens that exist for them.

**Offline.** A `ready` machine reads `offline` with the age only after it has sent a heartbeat and the last one is older than 15 minutes; it comes back to `ready` by itself on the next heartbeat. The setup-only service sends none, so such a machine never reads offline (the page says it cannot see whether the machine is on). An offline machine is never silently dropped and never revoked by the app.

**Revoke and re-enroll.** One close action: a waiting pairing is `cancelled` (the code stops working), a healthy connected one is `declined` ("This is not my machine"; credentials and grants are revoked), a failed or stalled one that was never approved is `abandoned`, an approved one is `revoked`. All use the existing invalidation (credentials, recovery, consent requests, grants), so a closed pairing leaves nothing usable. Revoking the machine under Runner machines in Admin or turning setup off closes the pairing as well (it reads `revoked`). "Set up again" is a new pairing with the same values: the owner view of a closed pairing carries the values to prefill, and the label is free again because the old machine is revoked.

**Member view.** Any signed-in member of the workspace may read the list: label, kind, state, step states and the sentence, with no code, no fingerprint, no grants and no ids. Members cannot create, accept or close; agent tokens get no access at all. A member sees "Ask the workspace owner to ..." as the next step.

**Concurrency and writes.** Every write is checked for the owner before the body is read, then runs in one control transaction with its audit rows. `request_id` makes create and accept idempotent (a replay returns the same record, with no code); a different body under the same id is `request_changed`. `version` is compare-and-set: a stale accept or close is `stale_version`. Every refusal is `{error, field?, reason}`; the sentence and next step for each `reason` come from `GET /api/compute/pairings/options`.

**Audit.** `runner.pairing.create`, `.accept`, `.close`, `.check` (denials only), `.report` (first report per step and every failure), with ids and fixed outcomes, never the code, the envelope secret or a key.

**Secrets.** The code appears in the creation response and in the command, nowhere else: no URL, no query string, no browser storage, no log, no audit row. The command puts the code on the machine's command line once; the line stays in that machine's shell history, where it is useless after first use or expiry (the app says so next to the command, with the leading space that keeps it out of history on shells that honour it). The envelope that accompanies it carries public values only.

**Not in slice 1 (the app says so).** Script (SSH) targets; independent owner approval keys; provider sign-in and binding attestation (they stay on the existing Needs me and Admin screens); a signed release channel for the launcher (B uses the hub's own origin and says so); starting or stopping anything on the machine; a QR code (a short code is not offered either: a short code would be a weaker secret).

#### Slices

- **A, server (this change):** `commonplace/compute/pairing.py`, `pairing_routes.py`, additive `issue_in`/`charge` parameters in `enrollment.py`, classification of the routes and tables, tests (denied non-owner, member read-only, agent token refused, stale/used/expired code, replay, wrong workspace, rate limits, CAS, idempotency, audit in the same transaction, offline, close and retry).
- **B, installer:** the launcher, the prerequisite checks, the step reports, tests with a fixture machine (no real host).
- **C, screens:** the guided flow in the Compute section for Classic and Deck, phone layouts, browser tests at 1280x800 and 390x844, screenshots.

#### Review round 2, server and installer

- **The window says why.** Every failure path on the machine prints the last collected installer lines and one fixed `Reason:` line (an installer refusal as it is, an operating-system error as its system message, anything else by kind; never the code, a token or an exception's own text), before the one next step. The app's "the window where you ran the command shows the reason on its last lines" is therefore true, including for a failed final check and a service that is not running.
- **A healthy earlier machine is never uninstalled.** Before removing what a different enrollment left, the machine asks the site that issued it, and only that site, about it with the old machine credential (`{"step": "probe"}` on `POST /api/runner/pairing-status`, which writes nothing). Only an answer of closed (or a credential that no longer works, or no credential at all) allows the removal; an open one stops with "This account already runs machine <label>. Remove it under Compute first." and nothing is touched; a site that cannot answer stops with "could not reach the site to check". A first try that Set up again cancelled is removed as before.
- **A lost connection at the exchange is the `files` step** (the checks passed; nothing was written), through the code route while the code is live.
- **Closing a failed setup.** The close reason `abandoned` ("Setup removed") keeps the owner's "This is not my machine" the only way to read "Not approved". Members read the owner's approval in the third person ("Machine connected, waiting for the owner's approval").
- **Smaller.** A 5xx answer to the machine's check is no answer (unreachable), not "the code cannot be used"; the machine's own failure is said even when the site is silent; a wrong-typed `cause` is a 400; refused checks are audited (id, reason, never the code); the launcher is fetched without following redirects; the missing runner program says to ask the person who runs the site for it (the app serves no runner guide); the fingerprint hint names the line "Machine fingerprint:" in the window; a ready machine's next step names Needs me for the provider sign-in.
- **Tests keep one clock.** The pairing tests' clock fixture freezes when it is created and moves only with `at(...)`; a stall or offline boundary is measured from one fixed start, so a slow run cannot read it a second short.

#### Review round 3, server and installer

- **A credential only goes to the site that issued it.** The stored machine credential is read only when the installation's manifest names the same site as the command; for any other site it does not exist, including when a failure is reported. A command for another site stops before any request or removal.
- **The window and the page agree.** After a spent code with nothing saved, the window says the app shows the setup as not finished after 15 minutes, which is when Set up again appears.
- **Smaller.** `request_id` must be a valid string whenever it is present for accept and close; a 5xx at the exchange is "delivery unavailable" (the code is not spent), not "the site did not accept the code".

#### Review round 4, pairing, installer and screens

- **Words that match the screen.** The window says "Cloud workspaces" (the screen's own title) where it said "Compute"; a refused administrator confirmation reads the same on the page ("The administrator confirmation was not given, or the password was wrong.") and in the window; the installer's "retry with the saved identity" and the service-manager sentence are in plain words; the copy fallback says to copy with the keyboard or the long-press menu.
- **A stalled setup is labelled "Not finished"** (owner and member, tone of a failure) instead of keeping the "waiting for your approval" chip.
- **Before any question.** A command for another site, or an installation whose manifest cannot be read, stops before the administrator confirmation (fail closed, nothing changed). A non-string `identity_digest` is a 400. When the final reports cannot reach the app, the window says so instead of "Done".
- **The overview's first row.** When the first machine arrives while the page is open, the first-run sentence is replaced at once (the state slot sits outside the fold).
- **A setup-only machine in the overview.** It has one reason in the "can this runner take new work" answer: "This setup only checks the machine. Coworkers do not run on it in this version." The chip stays "Set up and checked"; the blockers, the sentence and "Allowed to start card runs" ("No: this setup only checks the machine") say the same, with no offline, never-connected or not-approved claim, also after 15 minutes of silence and after the owner attests it. The ready copy and the intro say the same, and the attestation step is called "attest" everywhere (the card-run refusals said "vouch"). A cloud workspace beside only such machines says "No machine for a cloud workspace yet: the one you set up only checks itself in this version."
- **One name and one place for the confirmation.** A machine added through the guide is confirmed in Needs me ("Confirm this machine"; its card appears there once the provider sign-in is done). The overview's Not approved blocker, status sentence and next step, the ready copy, the approval note, the section note and the owner's line ("Confirm this machine in Needs me: not done yet") all say so; Admin's Attest, which needs a provider id an unguided machine has not got, is named only for machines that were not added through the guide, and the card-run refusals say "attest", not "vouch". A machine that is not approved now counts as needing attention in the overview summary.
- **Allowed names the holder.** "Yes, once a run finishes" is only said when a run will finish; an uncertain run says "Yes, once the uncertain run is resolved on its card" and a finished card still in Doing says "Yes, once the finished card leaves Doing". A turned-off runner says there is no control to turn it on again in this version.

#### Joint round 5, shared state and the card's start

- **One state for a guided machine that is not approved yet.** The overview reads the pairing's own state (`pairing.pending_machines`, the same `derive` and `stalled` the page uses) and shows the same chip, sentence and next step as Add a machine: "Waiting for your approval", or "Not finished" (a step failed, or stalled), Allowed "No: not approved yet", one blocker, counted as needing attention. "Disabled" is only for a runner the owner turned off.
- **The card's start.** A machine that exists but was added through the guide (waiting, not finished, or approved and never heard from) is never offered Start, never accepted for a start and never leased work. The refusal reads "The machine you added only checks itself in this version, so no Coworker runs on it yet." and links Needs me when a "Confirm this machine" card is up, else Add a machine. For an Admin-enrolled machine the refusal keeps Attest and names the provider instance id the form asks for.
- **The Needs me card.** It appears only after the machine has acknowledged its machine-access grant (`setup_approvals._prerequisites`); the guide's setup-only service does not acknowledge one and no provider sign-in is needed for the card, so in this version nothing more is to be done for such a machine. The copy says "Coworkers do not run on it in this version" everywhere and "Approving records the access listed above; nothing uses it in this version".
- **Smaller.** A stalled setup says "Choose Set up again, or Remove this machine."; the owner's own refusal of a connected machine is labelled "Refused" (so "Not approved" means one thing, in the overview); the form with no memory wings links Memory.

#### Screens (change C)

The Add a machine section sits on the Compute screen between the overview and the cloud workspaces, in Classic and in the Deck Management tab (one module, `commonplace/web/static/compute-pairing.js`). The owner's path, with the clicks counted: **Add a machine** (and **Turn on machine setup** once, if it is off), name the machine and say what it may read, **Create the command**, **Copy the command**, run it on the machine, **Approve this machine** when it appears. The page checks on the machine by itself while its state can still change (every three seconds, not in a hidden tab, and it says a state once when it changes); a settled state is never checked again.

What the person sees, per state, is the server's own sentence and next step. `Waiting for the machine` shows the three numbered run lines and the command (held in memory for this pairing only: leaving it, reloading or a replayed request shows "The command was shown once and is not kept" and offers a new one) and the four steps as Waiting. `Machine connected, waiting for your approval` shows the sheet: name, the fingerprint in the installer's groups once the machine has printed it (until then "Waiting for the machine to print its fingerprint."), what it may read, projects, topics, who can start work on it, what it may do without asking, how many cards it works on at a time, what approval grants and does not, with **Approve this machine** (available when all four steps are Done, as the server also requires) and **This is not my machine** (which asks first, on Go back). `Set up and checked` and `Offline` say what is true and that Coworkers can run only after a provider is connected and an owner attests the machine. A failed or stalled setup names the step and the cause and has one next step, **Set up again** (it cancels the old setup first, then opens the form with the same values, requesters included), with **Remove this machine** after it; steps that never ran read "Not run". `Code expired`, `Cancelled`, `Not approved`, `Setup removed` and `Access removed` offer **Set up again** with the same values filled in. **Cancel this setup** and **Remove this machine** are one action with the same wording as the server's close.

Honest limits shown on the page: the command does not install the runner program, the second kind (a script target) is listed as not available yet and cannot be chosen, and there is no turn-off control for machine setup here because turning it off removes every machine added this way.

Phones: the actions sit in the flow under the last field (no sticky or fixed bar, so nothing covers a field), buttons are full width and 44px tall on any touch screen, inputs are 16px, the command wraps instead of scrolling sideways, and a refusal's summary takes focus once while each field also shows its own message. Members read the same list with the server's member wording and no command, fingerprint, grant or control.

#### Review round 1, screens

- **Where to run the command.** Above the command, three numbered lines: open a terminal on that machine (Ubuntu: Super key, type Terminal, Enter), paste with Ctrl+Shift+V and press Enter without typing sudo in front, wait for the steps to turn to Done (the page updates itself). A note says that leaving the page loses the command ("you need a new command: this one is not kept") and the waiting step's button is "Make a new command (this one stops working)".
- **What approval grants.** The sheet says, above its buttons: approving lets the machine use the access listed above; it does not connect a provider; Coworkers cannot run on it until a provider is connected and an owner attests it under Runner machines in Admin. The sheet's words are plain ("Who can start work on it: nobody yet", "What it may do without asking", "Works on at most 1 card at a time"). **Approve is unavailable until all four steps are Done**, because the machine prints its fingerprint only as setup finishes: until then the sheet says "Waiting for the machine to print its fingerprint." and the button says why it waits, so the person never compares a fingerprint that is not there yet.
- **One next step for a failed or stalled machine.** **Set up again** comes first and is primary; it cancels the old setup (its name and machine would otherwise be in the way), then opens the form with the same values. **Remove this machine** follows. A machine that connected and did not finish within 15 minutes (`stalled`) shows the server's "This setup has not finished. Remove this machine and set it up again.", no Approve, and the same two buttons. The steps that never ran in a failed, stalled or closed setup read "Not run" (and "Done" for those that passed): one mapping for owner and member.
- **Confirm dialogs.** The safe answer comes first and takes focus: "Is this not your machine?" with **Go back** and "Yes, this is not my machine"; "Remove this machine?" with **Go back** and "Yes, remove it". Escape and Go back return focus to the button that asked. The sheet's "Approve this machine?" heading is not shown above the dialog.
