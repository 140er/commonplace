### Memory growth is bounded where it scales with workspaces, and a worker can recycle above a ceiling

- A production container sat near its memory limit and only a deploy reset it. The page cache of very large databases counts toward the container's cgroup, so part of that is reclaimable; the rest is anonymous memory in the gateway and in each worker, which is what can end in an out-of-memory kill. The Admin deploy view now splits the two, so the monitor can tell them apart.
- Decision: state that scales with workspaces is bounded or dropped with its worker (tools-list cache: 128 workspaces, warm-up table: last interval, clean restart circuits, storage meter: last minute), and an idle workspace's open thread store hands back its page cache after ten minutes while keeping its connection open, because callers hold store references and a closed connection would break them.
- Decision: the worker recycle ceiling (`COMMONPLACE_WORKER_RSS_RECYCLE_MB` on the gateway) is off by default. A worker's legitimate size follows its palace (index and embedding model), so any number shipped before it has been measured can make healthy workers restart in a loop, and every restart pays the cold load again. The operator sets it after sampling (see `deploy/commonplace/DEPLOY.md`). It counts anonymous memory only, never before ten minutes of uptime or two admitted calls, waits for a quiet moment unless a quarter over, and reuses the existing drain, restart circuit and replacement path; the container is never restarted.
- Not changed: the search path and its capacity-verdict reuse, the palace and embedding model a worker loads, and the gateway process itself, which has no recycle.
