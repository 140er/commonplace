### A flush window must not cost every search a cache drop and a wait

Round 3 of the search stall (15 Nov 2026). The deploy with the pause and start budgets still showed three things: a flat ~4.6 s per search for a dozen minutes (about 0.9 s earlier in the evening, the same on the previous deploy and after a container swap), busy answers that took 13 to 15 s although the budget is 5 s, and a stall of about five minutes that began right after agents initialised sessions (`startup context unavailable (TimeoutError)` in the log, no `memory call refused` line).

What the code does. The worker's search answers a transient index error (the HNSW flush window after writes) by dropping the palace caches, sleeping 2 s while it holds the request lock, and searching again on a freshly opened client; it did that for every search that met the error. A palace that stays in a flush window (writes keep arriving) therefore costs every search the 2 s wait, the cache reload and a second search, and searches that run together drop the handles the others use: the working explanation, to be confirmed by the new `search timings` log, of the flat ~4.6 s. Every `initialize` made the gateway send a memory search to the worker for the startup context although the context has 80 ms in all; the gateway gave up at once, the worker ran the search to the end, and the abandoned searches (and their cache drops) piled up: three of them in the 16 s before the last stall started. A busy answer was asked again by each of a search's later worker calls, each waiting out the lock bound.

Decision: one search per cooldown (30 s) drops the caches and waits; a search that meets the error again inside the cooldown is answered at once from the lexical index and carries `index_catching_up`. A worker call whose caller has under 0.25 s left on its deadline is not sent. A busy answer is asked once per request. The worker logs the timings of any search whose probe and first search took a second or more, the gateway logs worker calls of a second or more, and a refused index write logs the worker's own refusal, so the next stall names its wait. Not found: what holds searches for five minutes, and why the index job never gets past `units=0`; the refusal log line is what will say whether its writes are refused by a gate (a diverged index turns on the clock once its metadata is 300 s old).
