### Pipeline view: how each pull request is built and shipped (card #568)

Decision record and contract. Code: `commonplace/pipeline/` (data) and `deck-pipeline.js` (view); tests: `tests/test_pipeline_compute.py`, `tests/test_pipeline_api.py`, `tests/deck_pipeline.mjs`, `tests/test_deck_pipeline_browser.py`. On the base (`develop`) the `commonplace.pipeline` package does not exist, so the compute and API tests fail there with an import error and pass on the reviewed head.

**What it is.** A read-only Deck screen at `#/pipeline` (account menu, phone More sheet). Each pull request is a card of connected blocks: card, builder started, PR opened, gate, check, merge into develop, deploy (snapshot, rollback image, smoke, health), backup proof. A block shows its state in words (not started, queued, running, passed, failed, skipped), start, end and duration in Amsterdam time (`HH:MM:SS`, durations like `3m 12s`, `1h 04m`) and its links. The wait between two blocks is drawn on the connector. The header shows the total lead time (card start to a healthy deploy, or the time so far), the slowest step, the longest wait and where the PR is now.

**Events, not snapshots.** The data is an append-only log of events per pull request in the workspace file `pipeline.sqlite3` (tables `pipeline_prs`, `pipeline_events`), next to the other workspace stores, so it is encrypted with the workspace, covered by backups and never mixes workspaces. The server computes every number in one pure function (`compute.compute_pr`); the browser draws what it is given. Rules worth knowing: a step's run ends at its first pass, fail or skipped event and a later event starts a retry (the last run is shown, `attempts` counts them, `span` covers the first start to the last end); the wait before a step runs from the end of the nearest earlier step that has events to the start of its first run; a step that started before the previous one ended has `overlap` and no wait; the step after the last finished one carries a growing wait while the PR is open; a last step that failed ends the pipeline (later steps stay not started); an event id seen twice counts once; times never go negative.

**Writing events (the deploy script).** `POST /api/pipeline/events`, JSON body:

```
{"repo": "owner/name", "pr": 12, "title": "optional, up to 300 characters",
 "events": [{"id": "owner/name#12:gate:pass:1763200000", "step": "gate", "state": "pass",
             "at": "2026-11-15T10:30:00Z", "ref": "optional https link or short id",
             "detail": "optional short text"}]}
```

`step` is one of `card`, `builder`, `pr_opened`, `gate`, `check`, `merge`, `deploy_snapshot`, `deploy_rollback_image`, `deploy_smoke`, `deploy_health`, `backup_proof`; `state` is one of `pending`, `queued`, `running`, `pass`, `fail`, `skipped`. The script sends `builder` through `backup_proof`; the `card` step is built by the server (below), and recorded `card` events are kept but never shown. Event ids are unique per repository and PR (`<repo>#<pr>:<step>:<state>:<epoch>` is the agreed form); an id already recorded is a no-op, so a request can be repeated. Answer: `200 {"repo", "pr", "accepted", "duplicates"}`. A request is checked whole and stored in one transaction; one bad event stores nothing. Plain `400 {"error": "..."}` for: a body key, step or state that is not known; `at` that is not ISO 8601 (an offset is converted, no offset means UTC), more than five minutes in the future or before 2020; `repo` that is not `owner/name`; `pr` that is not a whole number from 1; `events` that is not a list of 1 to 200; an `id` that is not 1 to 120 plain characters; text longer than 300 characters or with control characters; text that looks like a secret (keys, tokens, passwords); more than 1000 events for one PR. `401` without a valid token, `403` for a connection that may not write.

**Token.** The script uses its own token with the one scope `pipeline:write`. The gateway allows it on `POST /api/pipeline/events` and refuses every other request with `403 {"error": "this connection can only record pipeline events"}`: no reads, no `/mcp`, no other route. It is a normal connection (only its hash is stored, shown once at creation, never logged), so it is workspace-scoped, can expire and can be revoked; a revoked or expired token answers `401`. It must be the only scope, belong to a workspace owner and have no parent, and a workspace has at most one live pipeline token: revoke before minting another (rotation). To mint, as the owner on the hub host, with the existing token command (the token is the only line on standard output):

```
commonplace token add pipeline-feed --workspace <workspace> --client deploy --scopes pipeline:write --by <owner email> > pipeline-token
```

Give the file's content to the deploy script as its bearer token (`Authorization: Bearer <token>`). Default life is 365 days (`--expires-days`). `commonplace token list --workspace <workspace>` shows its name, hint and state, never the token. To revoke or rotate: `commonplace token revoke pipeline-feed --workspace <workspace> --by <owner email>`, then mint again.

**Reading.** `GET /api/pipeline/prs?limit=20` (1 to 100, newest activity first) answers `{"demo": false, "prs": [...]}`; `GET /api/pipeline/prs/<owner>/<name>/<pr>` answers one PR or `404`. Reads use the normal signed-in session of any person in the workspace (an agent token with `memory:read` also reads). `?demo=1` answers a fixed example of three pull requests (a finished one, one whose first gate run failed and was retried, one just started) without touching the store; the screen offers it from its empty state. Each PR answer holds `repo`, `pr`, `title`, `state` (`running`, `done`, `failed`), `current_step`, `updated_at`, `lead` (`seconds`, `in_progress`, `from`, `to`, `basis` of `card` or `first_event`), `slowest`, `longest_wait` and `steps`; each step holds `step`, `label`, `present`, `state`, `attempts`, `events`, `queued_at`, `start`, `end`, `last_at`, `duration`, `first_start`, `span`, `running`, `wait` (`from_step`, `seconds`, `from`, `to`, `queued_seconds`, `ongoing`, `overlap`), `ref` and `detail`.

**The card step comes from the board.** The deploy script does not send it. On a read the server finds the board card for the PR number among the cards the reader may see (only numbers and times are used). A card stores the repository of its board when its PR was linked, which can be an older name of the repository the events carry, so the card is chosen like this: (1) a card whose PR repository is the event's repository or one of its aliases; (2) else, if exactly one visible card has this PR number, that card; (3) else the first card on a board whose repository is the event's repository or an alias; else no card. Aliases are `COMMONPLACE_REPO_ALIASES`, `old/name=new/name` pairs separated by commas (for example `owner/old-name=owner/new-name`), read both ways; malformed pairs are ignored. Nothing is matched across workspaces. The step is running at the card's first move to doing (else its creation), and passed when the PR opened (the `pr_opened` event; else the time the PR was reported on the card; else it keeps running). A card claimed after the PR opened is a zero-length step at the PR opening, marked "Card linked after the PR opened". The wait for the next step runs from the claim, and the card is never the slowest step because it spans the builder's work. With no linked card the step is skipped, says "No card" and the lead time starts at the first event.

**Decisions.** Event-sourced and computed on read, so the view and its numbers can change without rewriting data. Append-only: nothing is edited or deleted by the API. Retention is not capped yet beyond 1000 events per PR. A dedicated write-only scope instead of reusing `memory:write`, so the deploy host holds a credential that cannot read or change anything else. Deck-only, like the Compute map; Classic has no entry.
