### Projects under bots

Belongs to the Decisions about bots (see `docs/bots.md`, "Using bots in the web app"). The Deck sidebar shows one tree: each bot opens onto the projects (boards) filed under it, and a project with no bot of the person's sits under Unassigned.

**Where the link lives.** The link is per person, not per workspace: `bot_projects(user_id, board, bot_id, moved_at)` in the workspace file `bots.sqlite3`, primary key `(user_id, board)`. One person's bot owns 0..n projects and a project is under at most one of that person's bots. Bots are already per person (the personal "project" bot per board is created for each person), so the link follows the bots; a workspace-wide link would have to name one person's bot and leave every member's tree pointing at a bot they cannot see. A row with `bot_id` NULL records "moved to Unassigned" so the seeding below does not undo it. A project with no row is Unassigned. Nothing is deleted: archiving a bot keeps its rows (the project reads as Unassigned while the bot is archived and returns with it) and a link to a project the person can no longer read is simply not shown.

**Seeding (the migration).** `BotStore.ensure_defaults` (run on every `GET /api/bots` and every chat turn) calls `seed_projects`-style seeding (`BotStore._seed`) for the readable projects that have no row yet: first the person's live `kind='project'` bot whose `board` is that project, then the one live custom bot whose name equals the project's slug or name once case and punctuation are ignored (`fold`). Two bots that match leave the project Unassigned. It only inserts (`INSERT OR IGNORE`) and never moves or removes a link, so it is idempotent and safe to repeat. The table is created with `CREATE TABLE IF NOT EXISTS` when the file is opened, so a file written by an earlier release gains it without a rewrite; a backup taken before or after holds the same bots, messages and notes. It reaches a live workspace only through the normal deploy; nothing runs it by hand.

**Moving.** The bot's owner changes the tree (the same owner rule as `PATCH /api/bots/<id>`; a member who only holds a share of a bot gets 403, a bot that is not theirs is 404):

- `GET /api/bots/<id>/projects` returns `{projects}`, the slugs under the bot that the person can read.
- `PUT /api/bots/<id>/projects/<slug>` puts the project under the bot and returns the same shape; it answers 400 for a project the person cannot read or an archived bot.
- `DELETE /api/bots/<id>/projects/<slug>` puts the project back to Unassigned when it is under that bot (idempotent).

`GET /api/bots` adds `projects` (the slugs) to each bot; it is `[]` for a bot the person only holds a share of, so one person's arrangement is never shown to another. Both writes are web-session only (an app connection gets 404), and each real change is one audit row `bot_project:move` with the project slug and the bot ids it moved from and to, never text; a repeated request adds none.

**What members see.** The server lists only slugs of projects the caller can read; the browser draws Unassigned from the readable project list minus the placed ones, so a project the person cannot read never appears in the tree, a count or the Unassigned group, and a member cannot move another person's bot's projects.

**The tree in the browser.** `deck-tree.js` holds the pure parts (placement, the current node, keys, the per-device folded set under `cmmn.deck.tree.collapsed`); `deck-shell.js` draws it as `role="tree"` markup in the rail (`data-deck-bots`) and on the Bots screen of the phone layout (`data-deck-bots-page`). Rows open unless folded on this device; the row holding the page being viewed opens on arrival until the person folds it on that page. Arrow keys, Home and End move, Right and Left open, fold or step out, M (or the context menu key) opens the move chooser, and one row holds the tab stop. After a move the roster is read back from the server before the tree is redrawn.
