### Compute cloud workspaces: image, CPU, memory and storage in the app

A cloud workspace is meant to be a separate place on one of your Compute machines where Coworkers can run (the app says it that way: it is a plan until the start slice lands, never a fact about something that runs). A person creates it in the Compute screen with a Docker image, CPU, memory and storage limits, sees what it will use before saving, and changes it later. The current slice is the record: data model, owner REST API and the Compute form, list and detail. Starting and stopping the container belongs to the later machines, runners and workspaces slice, so every record says "Saved, not started" until then, and no sentence in the app promises that anything runs or is enforced; where the app mentions starting it says plainly that starting is not available yet.

#### What Compute already has (gap analysis, develop at the start of this slice)

- A "workspace" in Compute code always means the tenant (`Store.workspace_id`, `commonplace/compute/control.py`). There is no per-environment record: the stores hold gateways, targets (`nodes`), passive scopes, execution proposals and scripts (`_SCHEMA`, `control.py`). A target is an SSH-reachable machine; the topology map (`commonplace/topology/`) records machine facts (`RESOURCE_KEYS` cores, memory_gb, storage_gb in `model.py`) but nothing is bound to them.
- API: `/api/compute` (`routes.py`) is installed by `commonplace.compute.install`. Every request, including reads, is owner-only (`Store._owner`) except the cloud workspace reads below; a person of another workspace only sees their own store. Writes use the shared Origin and bounded-JSON boundary and fixed error codes; no MCP tool exists for Compute (the owner REST surface is the only one).
- UI: one module, `commonplace/web/static/compute.js` (`createCompute`), serves the Classic `#/compute` screen and the Deck Management tab (`deck-workspace.js` mounts it). It has forms for gateways, targets, scopes, proposals and scripts, an "Advanced" fold, and for a non-owner no management controls.
- Credentials (`docs/system/compute-credential-guide.md`): `GET /api/compute/credentials` lists reference rows; records can be saved without one and show "No credential bound yet"; `POST .../credential` binds a reference once. Credentials are never typed or created in the browser. The custody listing only returns the `gateway` and `target` purposes.
- Status pages (`docs/system/status-page.md`, `compute-status-line.md`): honest empty/off/failed wording and the rule that an unknown answer is explained, never blank.

#### Decisions

**What a workspace record is.** One row of `cloud_workspaces` in the existing per-workspace `compute.sqlite3` (explicit literal SQL, no table name in a format string, so the thread-store guard stays green). It describes what the machine will run, not what runs: a container created from the image with CPU, memory and storage limits, a workspace-scoped volume mounted as the Coworker's work directory, and a network policy. The machine is an enrolled target (`nodes` row) or empty ("no machine chosen yet"). The record is deliberately not an authority table of the execution fence: it grants nothing, and starting it later goes through the same approval and transport checks as every other Compute action. Columns added after the first release (`name_key`, `request_id`, `request_hash`) are added by `workspaces.schema` on open, which also backfills `name_key` for existing rows.

**Images.** Two sources. A short curated list the server owns (`GET /api/compute/workspaces/images`: Ubuntu 24.04, Debian 12 slim, Python 3.12 slim, Node.js 22 slim, all official library images, each with a one-line plain description) and "my own image" by address. A reference is validated against the container reference grammar: optional registry host with optional port, lowercase path, optional tag, optional `@sha256:<64 hex>` digest; at most 255 characters; no whitespace, quotes, shell characters, URL scheme, user info or leading dash, so a reference can never become an option or a shell word. Registry hosts are checked as well, by name and by address as typed: a host on a local or private network is refused (`registry_private`: loopback names and `localhost`, any host without a dot, suffixes `.local`, `.localhost`, `.internal`, `.lan`, `.home`, `.corp`, `.intranet`, `.private`, `.home.arpa`, `.localdomain`, `.svc`, `.ts.net` and `.consul`, each also as the bare name (`home.arpa/app`, `ts.net/app`), any label that is `localhost` or `localdomain` with an optional number (`localhost4.localdomain4`), and IP addresses in any notation other than plain dotted decimal, which covers loopback, link-local such as `169.254.169.254`, and the private, shared, documentation, benchmarking and reserved ranges). A public IPv4 address in plain dotted form is refused with its own reason (`registry_ip`: a registry has a name, and a pull by address cannot be checked here), and a login in the address (`user:pass@ghcr.io/app`, `pass@ubuntu`: any text after `@` that is not `algorithm:hex`) with `user_info`, which is never echoed or stored; neither is called a digest or a private network. A website name with no image path after it is refused (`registry_no_path`), so `ghcr.io:443` is never read as an image called `ghcr.io` with tag `443`; a lone dotted component counts as a website name only when a port follows it, when its last label is a common website ending (`com`, `io`, `org`, `net`, `dev`, `cloud`, `co`, `eu`, `uk`, `us`, `de`, `edu`, `gov`, `aws`), or when it is a local name or an address, so repositories such as `my.image`, `node.js` and `my.app:1.0` are accepted (a lone component is a repository on Docker Hub). A private registry is refused by name; resolution is checked when the image is pulled. A name that merely resolves to a private address through DNS cannot be seen here (`127.0.0.1.nip.io/app:1` is accepted), and nothing pulls an image yet, so no check of the resolved address exists. Checking the address a name resolves to at pull time is a requirement of the lifecycle card, not something this slice does. The app says "the publisher can update this version over time" for a tag and "locked to one exact version" for a digest; it does not ask a person to pin an image, because the app has no way to look a digest up. A curated image is stored as its exact curated reference; the digest it resolves to is recorded when the image is first pulled, never guessed here. References stored before the registry rules existed are still listed (`parse_image(..., strict=False)`); only new input is held to them.

**Registry logins (decision).** Private registries are hidden in the app and refused by the API until registry logins can really be stored, because the custody layer has no `registry` purpose: any typed or listed reference could have named a gateway or target SSH credential, and nothing would use it before the lifecycle slice. So: `private_registry: true` is refused on create and edit (`private_registry` / `unavailable`; a record that already says it needs one can keep saying so and can be made public); `POST /api/compute/workspaces/<id>/credential` always answers `409 conflict` / `registry_logins_unavailable` after the owner and concealment checks, reads no body and writes nothing; no registry login reference is returned in any projection; the form has no private-registry checkbox and no credential field; the image address hint says "Only public images work for now". `GET .../images` serves `registry_logins: false` so a client can tell. The later slice adds a `registry` custody purpose, a server-listed choice of stored logins with an honest empty state ("No logins are stored yet"), and a confirmation that a bound login cannot be changed; it replaces this refusal.

**Limits, ranges, defaults and sizes.** CPU 0.5 to 32 cores in steps of 0.5 (default 2); memory 512 to 131072 MiB in steps of 128 (default 4096, always shown as GiB in the app); storage 1 to 2048 GiB (default 20). The server also serves three preset sizes (`presets` in `GET .../images`: Small 1 CPU, 2 GiB, 10 GiB; Standard 2, 4, 20, the defaults; Large 4, 8, 50) that the form uses to fill the three fields; a test pins that each sits inside the ranges. Defaults apply when the field is omitted on create; out-of-range, non-numeric, boolean or wrongly stepped values are `invalid_request` and the form states the range next to the field. The API stores millicores for CPU. A machine-size check (request larger than the machine) needs live machine facts and happens when starting, with the failure reason `machine_too_small`; the app never claims a request fits.

**How limits will be enforced (the lifecycle card's design; none of this exists yet).** On the machine the container would be created with cgroup limits: `--cpus` (CPU quota), `--memory` with `--memory-swap` equal to it (no swap, so the memory limit is a hard limit), and `--pids-limit` as a fork-bomb ceiling. Storage is a per-workspace volume on a quota-capable filesystem (project quota or a size-bounded volume). If the machine cannot enforce a limit the start would fail with `limit_not_enforceable`; it never runs unbounded. None of this happens yet, so no hint in the form describes enforcement: each hint gives the range, the default and a "What do I need?" line with examples, and the form's note says starting is not available yet.

**At a limit: never silent.** Memory: the kernel kills the process, the container is marked out-of-memory and the status becomes Failed with reason `out_of_memory`. CPU: the container is throttled, not killed. Storage: writes fail; the status says `storage_full` and names the limit. The reason set is closed (`FAILURE_REASONS` in `commonplace/compute/workspaces.py`) and the UI maps each to a plain sentence; an unknown reason is shown as "Failed for a reason this page does not recognise" with what to do next (the owner checks the machine and reloads; a member is told the owner can), never blank, and a failed record shows its reason in the list row, not only in the details.

**Isolation.** One container per workspace, one volume per workspace, no shared mounts, no host paths, no Docker socket, a read-only root is not assumed. Network policy: `outbound` (default, shown as "Internet access allowed": its own network, no route to the machine's LAN, to the host or to other workspaces) or `none` (no network). Two workspaces on the same machine cannot see each other's volume or network. This too is applied when the workspace starts, and the form says so.

**Two counters, and what "started" means.** `version` counts every accepted edit, a rename included, and is what `expected_revision` is checked against (so a stale rename is refused like any other stale write); it is exposed on every record and sent back by the form and by discard. `revision` counts only the edits that need a restart (image, limits, network, machine) and drives the restart logic; the machine reports `applied_revision` when it last created the container. "Started" has one definition, `workspaces.has_started`: an `applied_revision` is set, or the state is not `pending`; a start that failed before anything was applied therefore counts, because it may have left a container or a volume behind. The machine lock, the `started` and `discardable` fields, the discard refusal and the History line all use that one helper.

**Changes waiting and status honesty.** A started workspace with `applied_revision < revision` has the status `restart_needed`, a status of its own, worded "Changes waiting" ("The saved settings are newer than the ones a machine applied. Starting is not available yet, so they are kept for its next start."). `ready` therefore always means the applied revision is current, and "ready" and "changes waiting" never describe the same record. `ready` can only be written by the start/stop lifecycle, which does not exist yet, so no live record shows it; its label is "Settings applied" ("A machine recorded that it applied the saved settings.") and no screen says "Ready", "running", "started" or "up to date" until a record really holds one. A state only a start can produce is worded as what a machine recorded ("The last recorded start failed. ..."), never as something this page did. `restart_needed` is also a boolean on the projection and stays true next to `failed` (and is false for a start that failed before applying anything). A name change never needs a restart. Moving a started workspace to another machine is refused (`conflict`, `machine_locked`) until a later step. There is no restart control in this slice, so no sentence offers one. One sentence per state is reused everywhere (form note, review, status, detail): not started ("Saved, not started. Starting is not available yet, so this only keeps your settings.") and started ("A start was recorded for this workspace. Changes to the image, limits or network are saved and apply at its next start; a new name applies at once."). "Starting is not available yet" is said once on any one screen.

**Safe defaults.** 2 CPU, 4 GiB memory, 20 GiB storage, network `outbound`, no machine chosen, no registry login, nothing started.

**Status model.** Derived by the server, one code and one plain reason: `no_machine` (no machine chosen yet), `needs_credential` (a record stored as private before logins were hidden; the app calls it "Private image" and says "Private images need a sign-in, and Commonplace can't store sign-ins yet, so only public images work for now. Choose a public image." (the one `PRIVATE_IMAGE` sentence: the form refusal, the failed-sign-in reason, the detail line and the unavailable-sign-in refusal all use it), with a Change image button for the owner), `pending` (machine chosen, "Saved, not started"), `restart_needed` ("Changes waiting"), `ready` ("Settings applied"), `failed` with a reason from `FAILURE_REASONS`. Only the later lifecycle code writes `ready`, `failed` and `applied_revision` (`Store._set_workspace_state`); the REST surface cannot. `ready` needs an `applied_revision` that covers the record's `revision`, checked in the same UPDATE that sets it, so a record can never be ready with settings the machine does not hold. Every status sentence says what is true and what to do now, and never leaves a dead end. One vocabulary for the slice: "Saved, not started", "Changes waiting", "Machine: <name>" everywhere (members: "Machine: assigned (name hidden)"; no machine: "Machine: not chosen yet"; "Saved, not started" has one tone whether or not a machine is chosen). Wording rule for the app: a saved record says what it is ("Saved, not started") and that starting is not available yet; it never says the settings are saved on a machine, that anything is enforced, or that anything runs.

**Names.** One rule on the server and in the browser: the name is normalised to NFC, counted in code points (1 to 60), must have no leading or trailing whitespace and none of: control, format (zero-width and bidirectional controls, byte order mark, tag characters), surrogate, private-use, unassigned, line or paragraph separator characters; the blank-looking letters and marks the category check cannot see (Hangul fillers U+115F, U+1160, U+3164 and U+FFA0, the braille blank U+2800, Khmer inherent vowels U+17B4 and U+17B5, the combining grapheme joiner U+034F, Mongolian variation selectors and the Mongolian free variation selector U+180B to U+180F, variation selectors U+FE00 to U+FE0F and U+E0100 to U+E01EF, the object replacement character U+FFFC); and any space other than U+0020 (a no-break or ideographic space inside a name is refused too). Every one of those is `characters`. A name must also contain at least one letter or digit (`no_letter`, so a name of only punctuation or emoji is refused). The accepted and refused names live in one shared fixture (`tests/fixtures/compute_workspace_inputs.json`) that the server suite and the browser-rule suite both read, as do the accepted and refused image references. Uniqueness uses `name_key`, the NFKC-case-folded form of the name (folded twice, a fixed point a test pins), so "Café" typed with a combining accent, "STRASSE" and "Straße", fullwidth "Ｂuild" and "Build", "Box ①" and "Box 1" and the ligature in "oﬃce" are one name; keys stored by the earlier rule are recomputed once by the migration (the oldest record keeps the plain key, a later collision is kept apart by its id); it is enforced by a unique index and checked in the transaction (`name_taken`). Renaming a record to a different casing of its own name is allowed.

**Cap and list.** The creation cap and the list limit are one number, 100 (`MAX_WORKSPACES`, served as `max_workspaces`), so a record made through the app is always listed. Records that already exist beyond it (data from before the cap, or written directly) are counted, not hidden silently: the list shows the newest 100, the response carries `total`, and the section says "Showing the newest 100 of N cloud workspaces"; one of those older records still opens by its id. At the cap, creation is refused with `limit_reached`, the New cloud workspace button is not shown and a sentence says why. Discarding a never-started workspace frees a place.

**Idempotent create.** `POST /api/compute/workspaces` takes an optional `request_id` (1 to 64 letters, digits, `-` and `_`); the form sends one per opened form and keeps it across a retry after a lost answer. The same id with the same values returns the earlier record (200 instead of 201, no second row); the same id with different values is `409 conflict` / `request_reused`. The hash of the accepted values is stored on the row with the id. A discarded record keeps its id in a tombstone table (`cloud_workspace_tombstones`, never deleted or changed: triggers refuse both), and replaying the create that made it is `409 conflict` / `request_discarded`, so a discard cannot be undone by a retry.

**Edits and stale writes.** The form remembers the values and the `version` it opened with and sends only the fields that changed plus `expected_revision` (the version). The server refuses a stale `expected_revision` (`conflict` / `stale_revision`) without changing anything, for a rename as for any other edit. If the list is reloaded while the form is open and the record's version moved, the form says so at once ("Someone else changed this workspace, so nothing was saved."; through the status line, taking no focus), shows what the person typed as they typed it (the raw field strings, an empty field as "(empty)"), really disables its submit (`disabled`) and puts "Reload to continue" beside it. Reloading opens a fresh form on the current values and keeps what was typed behind "Apply my changes again", which puts back only the fields the person had changed. A server `stale_revision` lands in the same place. An edit that changes nothing sends nothing. Cancel and Escape ask "Leave without saving?" when typed values would be lost; Escape from the review goes back to the form.

**Discard.** One verb, "discard", everywhere. A workspace that never started (`has_started` is false) can be discarded: `POST /api/compute/workspaces/<id>/discard` with `expected_revision` (the version), behind a confirmation rendered inside the record's own row, with fixed labels "Discard workspace" and "Keep it" (the name is in the sentence and the heading, so nothing overflows on a phone), "Keep it" focused by default and as strong as the danger-styled Discard, that says what happens ("removes the saved settings from Commonplace; nothing on a machine is affected; you can't undo this, but you can create it again"). If the server answers `already_started` (it started after the confirmation opened) the body is replaced by "It started after you opened this, so nothing was discarded. Keep it, or reload the list to see its current state.", Discard goes away and focus stays on "Keep it"; if the record changed (`stale_revision`) Discard is really disabled with its reason beside it. It is audited (`workspace.discarded`). A started workspace owns a container and a volume, so removing it has to stop the container and discard the volume, a destructive step with its own confirmation in the lifecycle slice; until then the detail of a started record says plainly "A started cloud workspace can't be discarded yet" and the API answers `409 conflict` / `already_started`. A record whose start failed counts as started, even if nothing was applied.

**Who can do what.** Owner: create, edit, discard, read. Member of the workspace: read-only list and details; the same rule in Classic and Deck. A member sees the name, the image address, the resources, the status and a note that a machine is assigned, and never a machine name, a machine id, an address, a host key or a registry reference (`machine_name` and `node_id` are null, `machine_assigned` says whether one is set); every write is `owner_required` (403), checked before any body is read. Cloud workspaces are one entry for everyone in both looks: the Deck bar lists "Cloud workspaces"; Classic lists "Cloud workspaces" as a first-level entry in the sidebar and as the third tab of the phone tab bar (and again in the account menu and the palette); the owner-only Compute map stays a separate entry. Putting it in the Classic sidebar replaces the earlier decision that the Classic rail is only Bots and Memory: the usability review found Compute was not reachable at a glance in Classic. A personal access token, even sent with the owner's cookie, is `owner_required` on every workspace route, reads included. Someone signed out is `sign_in` (401). A record of another workspace does not exist in this store, so it is `not_found` (404); this matches the rest of `/api/compute`. Create, edit and discard are audited in the append-only audit table.

**REST.** `GET /api/compute/workspaces` (list, newest first, at most 100, with `can_manage` and `total`), `GET /api/compute/workspaces/<id>`, `GET /api/compute/workspaces/images` (curated list, ranges, defaults, `presets`, `max_workspaces`, `registry_logins`), `POST /api/compute/workspaces` (create; optional `request_id`), `POST /api/compute/workspaces/<id>` (edit: changed fields plus `expected_revision`), `POST /api/compute/workspaces/<id>/discard` (`expected_revision`), `POST /api/compute/workspaces/<id>/credential` (always refused for now). No MCP tool: Compute has none, and this slice does not invent one.

**Error contract.** Every refusal on these routes (any path under `/api/compute/workspaces`, including a malformed one) is `{"error": <code>, "reason": <reason>}` plus `"field"` when it is about one form field; the browser words each (field, reason) pair beside its field or, without a field, in the form summary. Other Compute routes keep their fixed bare shape. The path is decoded before any decision, so an encoded segment (`/%77orkspaces`) is the route it really is. The owner check comes first, then a foreign record is concealed, then the body is read. Codes:

- 400 `invalid_request`: `identifier` (the id in the path is not an identifier), `query` (a query string or fragment), `request` (the shared write boundary refused the request: a missing, foreign or repeated Origin, a request that is not JSON, or framing; mapped by the boundary's code, so it is never reported as `owner_required` to the owner), `body` (not bounded JSON), `unknown_field`, `required` (field named), `no_changes`, `invalid` (`request_id`, `expected_revision`), and per field: `name` (`length`, `characters`, `no_letter`), `image` (`empty`, `too_long`, `scheme`, `characters`, `user_info`, `digest`, `tag`, `registry`, `registry_private`, `registry_ip`, `registry_no_path`, `name`, `not_curated`), `image_source` (`choice`), `cpu_cores` / `memory_mib` / `storage_gib` (`not_a_number`, `range`, `step`; a huge integer is `range`, never a server error), `network` (`choice`), `node_id` (`choice`), `private_registry` (`choice`, `unavailable`).
- 401 `sign_in` / `session`; 403 `owner_required` / `member` (the caller is not the owner person; a personal access token never is); 404 `not_found` / `record` (no such record in this workspace), `route` (no such path) or `node_id` / `unknown_machine`; 503 `authority_unavailable` / `authority`.
- 409 `conflict`: `name_taken` (`name`), `stale_revision`, `machine_locked` (`node_id`), `limit_reached`, `request_reused` and `request_discarded` (`request_id`), `already_started`, `registry_logins_unavailable`.

**Names and unreadable references (round 5).** Name uniqueness is decided from the names, not from the stored keys: `_taken` folds every other record's name again (`name_key`), so a record the migration kept apart under `key\x00id` still blocks the name it folds to, and a rename into it is `name_taken`; an `IntegrityError` on the UPDATE (the `name` column is unique on its own) is mapped to the same `name_taken`, never a 500. A record whose stored image reference can no longer be parsed does not fail the list: `public` projects it as `image_unreadable: true` with an empty `image` and no registry, tag or digest, and every other row is served as usual. The Compute control journal turns only the protocol's own refusals (`ProtocolDenied`, `ScopeDenied`) into a store error; a `TypeError` or `OverflowError` is a bug and propagates.

**Schema and migration.** Columns and tables added after the first release (`name_key`, `request_id`, `request_hash`, `version`, the tombstone table and its triggers) are added by `workspaces.schema`, which runs once per database: `PRAGMA user_version` records the step done (`SCHEMA_VERSION`, 3), so an ordinary Compute transaction pays for one read. The whole migration is one `BEGIN IMMEDIATE` transaction (the version is re-read under the lock, and `user_version` is written last), so a crash between two steps leaves the database exactly as it was and the next open runs every step again; a test fails the backfill part-way and checks that. It fills `version` from `revision` and recomputes `name_key` for every row (keeping stored names unique by key). The list, the detail and the idempotent-replay lookup read the machine's name in the same query (one shared SELECT with a JOIN), not one lookup per row; a test counts the statements and shows the count does not grow with the number of records.

**No machine at all (round 5).** When no machine is set up, the Machine field reads "No machines set up yet" and is disabled, and the record says "No machine is set up yet, so this stays on Choose later. Starting will need one; that is not available yet." instead of telling the owner to choose a machine that cannot be chosen; "Choose a machine for it with Change settings." appears only when a machine exists, and no sentence points at the SSH settings. A record whose stored image cannot be read (`image_unreadable`) is listed as "Image unreadable" with its own sentence. A refused discard changes the row's status to "Started since you opened this" in the same render as the refusal, and the reason is the accessible description of "Keep it", where focus lands, so it is read once. The stale-edit and leave-confirm rows wrap onto 44px rows (one button per row at 320px) instead of clipping.

**Deck (round 5).** The Deck entry and page are called "Cloud workspaces"; its two tabs are Map (the machines, with one line saying so, and the route highlight card, which belongs with the map it highlights) and Management (the cloud workspaces). A member has nothing on the map and nothing to manage, so the member gets the one read-only page without a tab bar.

**UI.** A "Cloud workspaces" section opens the Compute management screen in Classic and Deck (one shared module, `commonplace/web/static/compute-workspaces.js`). The section defines a cloud workspace once. The page is called "Cloud workspaces" in both looks (the section heading is "Your cloud workspaces"); the refresh button is "Refresh"; the technical sections (gateways, targets, passive scopes, scripts, passive observations, execution proposals) all sit behind one "Advanced" disclosure. Rows show the name (a heading), one plain status, one resource line, one machine line, the image and, for a failed record, its reason; the row's buttons name their workspace ("Details for Build box"; the detail view's buttons too); Discard is danger-styled and set apart; a panel (form, review, details) replaces the row it is about, and the discard confirmation renders inside it. The form has name (with an example), image (curated choices plus "My own image…": the address box appears in place (it is only hidden while a ready-made image is chosen, so nothing repaints or scrolls) with a plain lead sentence, "The name of the image, for example ubuntu:24.04. Not sure? Pick a ready-made image above.", no placeholder, and a "Where do I find it?" disclosure that holds the one definition of a registry, the "docker pull" tip and what public means; the review names the chosen image first ("Ubuntu 24.04 (docker.io/library/ubuntu:24.04)")), three preset sizes (Small, Standard, Large) that fill the fields and stay editable, CPU cores, memory in GiB and storage each with a range, a default and a "What do I need?" line with examples, network and machine ("Choose later" or an enrolled machine by name). Required fields are marked. A field is validated when it is committed (change or blur) and when the form is submitted, never per keystroke, so nothing is announced while typing; fixing a shown problem clears it quietly, and a commit made on the way to a button is held until the pointer is released so the click is not lost to a layout shift. An invalid input or select gets a red edge, an icon and a red message (a polite live region, read through `aria-describedby` when its control takes focus, so nothing is read twice). A failed submit (or a refusal from the server) opens a summary at the top that lists the fields in error as links and takes focus; each link jumps to its field. The resource preview shows "Fix the highlighted fields to see what this will use." while a resource value is invalid and always uses GiB. Saving keeps focus on the pressed button, marks the section `aria-busy` and says "Saving…" in the status line; the status line is never focused: after saving, focus goes to the saved row's heading (to "New cloud workspace" after a discard, to the section heading after a reload). Escape closes a panel (one step back at a time, asking before typed values are lost); closing returns focus to the button that opened it. "Comes from" names the registry in words ("GitHub Container Registry (ghcr.io)"), History says "Edited once" or "Edited 3 times". Sizes follow the pointer as well as the width (`@media (pointer: coarse), (max-width: 699px)`): on a phone and on any touch device, a 768px tablet included, inputs are 16px, labels, hints, errors and size captions 14px, and every target (the summary's links too, each a full-height list item) at least 44px. On the phone (Classic and Deck share the 699px breakpoint) the layout changes too: the form's actions are one 44px row (Review and Cancel side by side) that sticks to the bottom of the page scroller: just above the tab bar in Classic, flush with the end of the scroller in Deck (in Deck `#content` stays the scroller, so a touch swipe scrolls the form). Fields scroll clear of that bar. The two bottom offsets are the custom properties `--ws-bar-h` and `--ws-tab-h`.
