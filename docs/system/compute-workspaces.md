### Compute cloud workspaces: image, CPU, memory and storage in the app

A cloud workspace is an isolated environment on one Compute machine where Coworkers run. A person creates it in the Compute screen with a Docker image, CPU, memory and storage limits, sees what it costs in resources before saving, and changes it later. Slice 1 (card 614) is the record: data model, owner REST API and the Compute form, list and detail. Starting and stopping the container is the later machines, runners and workspaces card (615), so every record says "Not started yet" until then.

#### What Compute already has (gap analysis, develop at the start of this slice)

- A "workspace" in Compute code always means the tenant (`Store.workspace_id`, `commonplace/compute/control.py`). There is no per-environment record: the stores hold gateways, targets (`nodes`), passive scopes, execution proposals and scripts (`_SCHEMA`, `control.py`). A target is an SSH-reachable machine; the topology map (`commonplace/topology/`) records machine facts (`RESOURCE_KEYS` cores, memory_gb, storage_gb in `model.py`) but nothing is bound to them.
- API: `/api/compute` (`routes.py`) is installed by `commonplace.compute.install`. Every request, including reads, is owner-only (`Store._owner`); a member gets `owner_required` (403), a person of another workspace only sees their own store. Writes use the shared Origin and bounded-JSON boundary and fixed error codes; no MCP tool exists for Compute (the owner REST surface is the only one).
- UI: one module, `commonplace/web/static/compute.js` (`createCompute`), serves the Classic `#/compute` screen and the Deck Management tab (`deck-workspace.js` mounts it). It has forms for gateways, targets, scopes, proposals and scripts, an "Advanced" fold, and for a non-owner only the sentence "Compute management requires the current workspace owner."
- Credentials (G09, `docs/system/compute-credential-guide.md`): `GET /api/compute/credentials` lists reference rows; records can be saved without one and show "No credential bound yet"; `POST .../credential` binds a reference once (`Store.bind_credential`). Credentials are never typed or created in the browser. The listing only returns the `gateway` and `target` purposes.
- Status pages (G20/G23, `docs/system/status-page.md`, `compute-status-line.md`): honest empty/off/failed wording and the rule that an unknown answer is explained, never blank.
- Missing for "a person creates a cloud workspace with an image, CPU and memory in the app": a workspace record and its table, image reference rules, limit ranges, a status model, a member read path, the form with resource preview, and the honest "not started" state. Container start and stop, real usage and the registry credential purpose are out of this slice.

#### Decisions

**What a workspace record is.** One row of `cloud_workspaces` in the existing per-workspace `compute.sqlite3` (explicit literal SQL, no table name in a format string, so the thread-store guard A4 stays green). It describes what the machine will run, not what runs: a container created from the image with CPU, memory and storage limits, a workspace-scoped volume mounted as the Coworker's work directory, and a network policy. The machine is an enrolled target (`nodes` row) or empty ("no machine bound yet"). The record is deliberately not an authority table of the execution fence: it grants nothing, and starting it later goes through the same approval and transport checks as every other Compute action.

**Images.** Two sources. A short curated list the server owns (`GET /api/compute/workspaces/images`: Ubuntu 24.04, Debian 12 slim, Python 3.12 slim, Node.js 22 slim, all official library images) and "my own image" by reference. A reference is validated against the container reference grammar: optional registry host with optional port, lowercase path, optional tag, optional `@sha256:<64 hex>` digest; at most 255 characters; no whitespace, quotes, shell characters, URL scheme, user info or leading dash, so a reference can never become an option or a shell word. A tag alone is accepted but shown as "Not pinned: the tag can change"; a digest is shown as "Pinned to <first 12 digest characters>" and recommended in the form. A curated image is stored as its exact curated reference; the digest it resolves to is recorded when the image is first pulled (card 615), never guessed here. Private registries: a record marks "needs a registry login" and carries only a credential reference (id and version, bound once like a gateway's, G09 pattern). No password, token or key is typed in the browser or stored in this table. Until one is bound the status is "No credential bound yet" and the record cannot start. The custody purpose for registry logins and its use at pull time arrive with card 615; slice 1 stores the reference only.

**Limits, ranges and defaults.** CPU 0.5 to 32 cores in steps of 0.5 (default 2); memory 512 to 131072 MiB in steps of 128 (default 4096, shown as GiB when whole); storage 1 to 2048 GiB (default 20). Defaults apply when the field is omitted on create; out-of-range, non-numeric, boolean or wrongly stepped values are `invalid_request` and the form states the range next to the field. The API stores millicores for CPU. A machine-size check (request larger than the machine) needs live machine facts and happens when starting (card 615) with the failure reason `machine_too_small`; slice 1 never claims a request fits.

**How limits are enforced (when started).** On the machine the container is created with cgroup limits: `--cpus` (CPU quota), `--memory` with `--memory-swap` equal to it (no swap, so the memory limit is a hard limit), and `--pids-limit` as a fork-bomb ceiling. Storage is a per-workspace volume on a quota-capable filesystem (project quota or a size-bounded volume). If the machine cannot enforce a limit the start fails with `limit_not_enforceable`; it never runs unbounded.

**At a limit: never silent.** Memory: the kernel kills the process, the container is marked out-of-memory and the status becomes Failed with reason `out_of_memory` ("ran out of memory at 4 GiB; raise the memory limit and restart"). CPU: the container is throttled, not killed; the detail says "running at its CPU limit" when throttling is observed. Storage: writes fail; the status says `storage_full` and names the limit. The reason set is closed (`FAILURE_REASONS` in `commonplace/compute/workspaces.py`) and the UI maps each to a plain sentence; an unknown reason is shown as "Failed: reason not recognised", never blank.

**Isolation.** One container per workspace, one volume per workspace, no shared mounts, no host paths, no Docker socket, a read-only root is not assumed. Network policy: `outbound` (default: its own network, internet out, no route to the machine's LAN, to the host or to other workspaces) or `none` (no network). Two workspaces on the same machine cannot see each other's volume or network.

**Restart needed.** Every edit of image, limits, network or machine bumps `revision`; the machine reports `applied_revision` when it last created the container. `restart_needed` is true when a started workspace has `applied_revision < revision`; the list and detail say "Restart needed to apply the new limits" and the editor says so before saving. A workspace that was never started says "Not started yet: changes apply when it starts". A name change never needs a restart. Moving a started workspace to another machine is refused (`conflict`) until a later step.

**Safe defaults.** 2 CPU, 4 GiB memory, 20 GiB storage, network `outbound`, no machine chosen, no registry login, tag-or-digest shown, nothing started.

**Status model.** Derived by the server, one code and one plain reason: `no_machine` (no machine bound yet), `needs_credential` (private registry without a bound credential: "No credential bound yet"), `pending` (machine chosen, "Not started yet"), `ready`, `failed` with a reason from `FAILURE_REASONS`. Only the lifecycle code of card 615 writes `ready` and `failed` and `applied_revision` (`Store._set_workspace_state`); the REST surface cannot.

**Who can do what.** Owner: create, edit, bind a registry reference, read. Member of the workspace: read-only list and detail (no registry reference, no addresses); every write is `owner_required` (403). Someone signed out is `sign_in` (401). A record of another workspace does not exist in this store, so it is `not_found` (404); this matches the rest of `/api/compute`. Create and edit are audited in the append-only audit table. No delete in slice 1: removing a workspace has to stop the container and discard its volume, which is a destructive step with its own confirmation in card 615.

**REST.** `GET /api/compute/workspaces` (list, newest first, at most 100, with `can_manage`), `GET /api/compute/workspaces/<id>`, `GET /api/compute/workspaces/images` (curated list, ranges, defaults), `POST /api/compute/workspaces` (create), `POST /api/compute/workspaces/<id>` (edit; carries `expected_revision`, a stale one is `conflict`), `POST /api/compute/workspaces/<id>/credential` (bind once). No MCP tool: Compute has none, and this slice does not invent one.

**UI.** A "Cloud workspaces" section opens the Compute management screen in Classic and Deck (one shared module, `commonplace/web/static/compute-workspaces.js`). The form has name, image (curated choices plus "My own image"), CPU, memory, storage, network, machine ("Choose later" or an enrolled machine) and shows the resource preview ("2 CPU, 4 GiB memory, 20 GiB storage on <machine>", or "No machine chosen yet") before the save button. Each field validates inline with the range and the reason. Lists and detail never render empty: every state has a sentence. Coworkers are called Coworkers. Members see the same list and detail without any edit control and with a sentence saying who can change it.
