### Compute cloud workspaces: image, CPU, memory and storage in the app

A cloud workspace is an isolated environment on one Compute machine where Coworkers run. A person creates it in the Compute screen with a Docker image, CPU, memory and storage limits, sees what it will use before saving, and changes it later. The current slice is the record: data model, owner REST API and the Compute form, list and detail. Starting and stopping the container belongs to the later machines, runners and workspaces slice, so every record says "Not started yet" until then, and every sentence about running or enforcement in the app is written as "once workspaces can start".

#### What Compute already has (gap analysis, develop at the start of this slice)

- A "workspace" in Compute code always means the tenant (`Store.workspace_id`, `commonplace/compute/control.py`). There is no per-environment record: the stores hold gateways, targets (`nodes`), passive scopes, execution proposals and scripts (`_SCHEMA`, `control.py`). A target is an SSH-reachable machine; the topology map (`commonplace/topology/`) records machine facts (`RESOURCE_KEYS` cores, memory_gb, storage_gb in `model.py`) but nothing is bound to them.
- API: `/api/compute` (`routes.py`) is installed by `commonplace.compute.install`. Every request, including reads, is owner-only (`Store._owner`) except the cloud workspace reads below; a person of another workspace only sees their own store. Writes use the shared Origin and bounded-JSON boundary and fixed error codes; no MCP tool exists for Compute (the owner REST surface is the only one).
- UI: one module, `commonplace/web/static/compute.js` (`createCompute`), serves the Classic `#/compute` screen and the Deck Management tab (`deck-workspace.js` mounts it). It has forms for gateways, targets, scopes, proposals and scripts, an "Advanced" fold, and for a non-owner no management controls.
- Credentials (`docs/system/compute-credential-guide.md`): `GET /api/compute/credentials` lists reference rows; records can be saved without one and show "No credential bound yet"; `POST .../credential` binds a reference once. Credentials are never typed or created in the browser. The custody listing only returns the `gateway` and `target` purposes.
- Status pages (`docs/system/status-page.md`, `compute-status-line.md`): honest empty/off/failed wording and the rule that an unknown answer is explained, never blank.

#### Decisions

**What a workspace record is.** One row of `cloud_workspaces` in the existing per-workspace `compute.sqlite3` (explicit literal SQL, no table name in a format string, so the thread-store guard stays green). It describes what the machine will run, not what runs: a container created from the image with CPU, memory and storage limits, a workspace-scoped volume mounted as the Coworker's work directory, and a network policy. The machine is an enrolled target (`nodes` row) or empty ("no machine chosen yet"). The record is deliberately not an authority table of the execution fence: it grants nothing, and starting it later goes through the same approval and transport checks as every other Compute action. Columns added after the first release (`name_key`, `request_id`, `request_hash`) are added by `workspaces.schema` on open, which also backfills `name_key` for existing rows.

**Images.** Two sources. A short curated list the server owns (`GET /api/compute/workspaces/images`: Ubuntu 24.04, Debian 12 slim, Python 3.12 slim, Node.js 22 slim, all official library images, each with a one-line plain description) and "my own image" by address. A reference is validated against the container reference grammar: optional registry host with optional port, lowercase path, optional tag, optional `@sha256:<64 hex>` digest; at most 255 characters; no whitespace, quotes, shell characters, URL scheme, user info or leading dash, so a reference can never become an option or a shell word. Registry hosts are checked as well: a host on a local or private network is refused (`registry_private`: loopback names and `localhost`, any host without a dot, suffixes `.local`, `.localhost`, `.internal`, `.lan`, `.home`, `.corp`, `.intranet`, `.private`, `.home.arpa`, and IP addresses in any notation, which covers loopback, link-local such as `169.254.169.254`, and the private ranges), and a registry with no image path is refused (`registry_no_path`), so `ghcr.io:443` is never read as an image called `ghcr.io` with tag `443`. A name that merely resolves to a private address through DNS cannot be seen here (`127.0.0.1.nip.io/app:1` is accepted), and nothing pulls an image yet, so no check of the resolved address exists. Checking the address a name resolves to at pull time is a requirement of the lifecycle card, not something this slice does. The app says "the publisher can update this version over time" for a tag and "locked to one exact version" for a digest; it does not ask a person to pin an image, because the app has no way to look a digest up. A curated image is stored as its exact curated reference; the digest it resolves to is recorded when the image is first pulled, never guessed here. References stored before the registry rules existed are still listed (`parse_image(..., strict=False)`); only new input is held to them.

**Registry logins (decision).** Private registries are hidden in the app and refused by the API until registry logins can really be stored, because the custody layer has no `registry` purpose: any typed or listed reference could have named a gateway or target SSH credential, and nothing would use it before the lifecycle slice. So: `private_registry: true` is refused on create and edit (`private_registry` / `unavailable`; a record that already says it needs one can keep saying so and can be made public); `POST /api/compute/workspaces/<id>/credential` always answers `409 conflict` / `registry_logins_unavailable` after the owner and concealment checks, reads no body and writes nothing; no registry login reference is returned in any projection; the form has no private-registry checkbox and no credential field; the image address hint says "Only public images work for now". `GET .../images` serves `registry_logins: false` so a client can tell. The later slice adds a `registry` custody purpose, a server-listed choice of stored logins with an honest empty state ("No logins are stored yet"), and a confirmation that a bound login cannot be changed; it replaces this refusal.

**Limits, ranges, defaults and sizes.** CPU 0.5 to 32 cores in steps of 0.5 (default 2); memory 512 to 131072 MiB in steps of 128 (default 4096, always shown as GiB in the app); storage 1 to 2048 GiB (default 20). The server also serves three preset sizes (`presets` in `GET .../images`: Small 1 CPU, 2 GiB, 10 GiB; Standard 2, 4, 20, the defaults; Large 4, 8, 50) for the form to fill the three fields with; a test pins that each sits inside the ranges. Defaults apply when the field is omitted on create; out-of-range, non-numeric, boolean or wrongly stepped values are `invalid_request` and the form states the range next to the field. The API stores millicores for CPU. A machine-size check (request larger than the machine) needs live machine facts and happens when starting, with the failure reason `machine_too_small`; the app never claims a request fits.

**How limits are enforced (when started).** On the machine the container is created with cgroup limits: `--cpus` (CPU quota), `--memory` with `--memory-swap` equal to it (no swap, so the memory limit is a hard limit), and `--pids-limit` as a fork-bomb ceiling. Storage is a per-workspace volume on a quota-capable filesystem (project quota or a size-bounded volume). If the machine cannot enforce a limit the start fails with `limit_not_enforceable`; it never runs unbounded. None of this happens yet, and the form says so: each limit's hint reads "Once workspaces can start, ...".

**At a limit: never silent.** Memory: the kernel kills the process, the container is marked out-of-memory and the status becomes Failed with reason `out_of_memory`. CPU: the container is throttled, not killed. Storage: writes fail; the status says `storage_full` and names the limit. The reason set is closed (`FAILURE_REASONS` in `commonplace/compute/workspaces.py`) and the UI maps each to a plain sentence; an unknown reason is shown as "Failed: reason not recognised", never blank.

**Isolation.** One container per workspace, one volume per workspace, no shared mounts, no host paths, no Docker socket, a read-only root is not assumed. Network policy: `outbound` (default, shown as "Internet access allowed": its own network, no route to the machine's LAN, to the host or to other workspaces) or `none` (no network). Two workspaces on the same machine cannot see each other's volume or network. This too is applied when the workspace starts, and the form says so.

**Two counters, and what "started" means.** `version` counts every accepted edit, a rename included, and is what `expected_revision` is checked against (so a stale rename is refused like any other stale write); it is exposed on every record and is what a client sends back on edit and on discard. `revision` counts only the edits that need a restart (image, limits, network, machine) and drives the restart logic; the machine reports `applied_revision` when it last created the container. "Started" has one definition, `workspaces.has_started`: an `applied_revision` is set, or the state is not `pending`; a start that failed before anything was applied therefore counts, because it may have left a container or a volume behind. The machine lock, the `started` and `discardable` fields, the discard refusal and the History line all use that one helper.

**Restart needed and status honesty.** The machine reports `applied_revision` when it last created the container. A started workspace with `applied_revision < revision` has the status `restart_needed`, a status of its own ("Restart needed": "Its saved settings changed after it last started. The new settings apply when it is restarted."). `ready` therefore always means the applied revision is current, and "ready" and "restart needed" never describe the same record. `restart_needed` is also a boolean on the projection and stays true next to `failed` (and is false for a start that failed before applying anything). A workspace that was never started says "Not started yet: changes apply when it first starts". A name change never needs a restart. Moving a started workspace to another machine is refused (`conflict`, `machine_locked`) until a later step. There is no restart control in this slice, so no sentence offers one.

**Safe defaults.** 2 CPU, 4 GiB memory, 20 GiB storage, network `outbound`, no machine chosen, no registry login, nothing started.

**Status model.** Derived by the server, one code and one plain reason: `no_machine` (no machine chosen yet), `needs_credential` (a record stored as private before logins were hidden: "Needs a registry login"), `pending` (machine chosen, "Not started yet"), `restart_needed`, `ready`, `failed` with a reason from `FAILURE_REASONS`. Only the later lifecycle code writes `ready`, `failed` and `applied_revision` (`Store._set_workspace_state`); the REST surface cannot. Wording rule for the app: a saved record says "Saved in Commonplace. Nothing has been sent to the machine yet."; it never says the settings are saved on a machine, that anything is enforced, or that anything runs, except in sentences that start "Once workspaces can start".

**Names.** One rule on the server and in the browser: the name is normalised to NFC, counted in code points (1 to 60), must have no leading or trailing whitespace and none of: control, format (zero-width and bidirectional controls, byte order mark, tag characters), surrogate, private-use, unassigned, line or paragraph separator characters; the blank-looking letters and marks the category check cannot see (Hangul fillers U+115F, U+1160, U+3164 and U+FFA0, the braille blank U+2800, Khmer inherent vowels U+17B4 and U+17B5, the combining grapheme joiner U+034F, Mongolian variation selectors U+180B to U+180D, variation selectors U+FE00 to U+FE0F and U+E0100 to U+E01EF); and any space other than U+0020 (a no-break or ideographic space inside a name is refused too). Every one of those is `characters`. A name must also contain at least one letter or digit (`no_letter`, so a name of only punctuation or emoji is refused). The accepted and refused names live in one shared fixture (`tests/fixtures/compute_workspace_inputs.json`), as do the accepted and refused image references; the server suite reads it and the browser rule is checked against the same list. Uniqueness uses `name_key`, the NFC form of the case-folded name, so "Café" typed with a combining accent, "STRASSE" and "Straße" are one name; it is enforced by a unique index and checked in the transaction (`name_taken`). Renaming a record to a different casing of its own name is allowed.

**Cap and list.** The creation cap and the list limit are one number, 100 (`MAX_WORKSPACES`, served as `max_workspaces`), so a record made through the app is always listed. Records that already exist beyond it (data from before the cap, or written directly) are counted, not hidden silently: the list shows the newest 100 and the response carries `total`; one of those older records still opens by its id. At the cap, creation is refused with `limit_reached`, the New cloud workspace button is disabled and says why. Discarding a never-started workspace frees a place.

**Idempotent create.** `POST /api/compute/workspaces` takes an optional `request_id` (1 to 64 letters, digits, `-` and `_`); the form sends one per opened form and keeps it across a retry after a lost answer. The same id with the same values returns the earlier record (200 instead of 201, no second row); the same id with different values is `409 conflict` / `request_reused`. The hash of the accepted values is stored on the row with the id. A discarded record keeps its id in a tombstone table (`cloud_workspace_tombstones`, never deleted or changed: triggers refuse both), and replaying the create that made it is `409 conflict` / `request_discarded`, so a discard cannot be undone by a retry.

**Edits and stale writes.** The form remembers the values and the `version` it opened with and sends only the fields that changed plus `expected_revision` (the version). If the list was reloaded while the form was open and the record's revision or update time moved, the form does not send: it says "This workspace changed while you were editing. Close this form, reload the list, and make your change again." The server also refuses a stale `expected_revision` (`conflict` / `stale_revision`) without changing anything, for a rename as for any other edit. An edit that changes nothing sends nothing.

**Delete and discard.** A workspace that was never started (never applied, state `pending`) can be discarded: `POST /api/compute/workspaces/<id>/discard` with `expected_revision` (the version), behind a confirmation that says what happens ("removes the saved settings from Commonplace; nothing on a machine is affected; you can't undo this, but you can create it again"). It is audited (`workspace.discarded`). A started workspace owns a container and a volume, so removing it has to stop the container and discard the volume, a destructive step with its own confirmation in the lifecycle slice; until then the detail and the review say plainly "A cloud workspace that has been started can't be deleted yet" and the API answers `409 conflict` / `already_started`. A record whose start failed counts as started, even if nothing was applied. The create request id of a discarded record stays in a tombstone.

**Who can do what.** Owner: create, edit, discard, read. Member of the workspace: read-only list and details; the same rule in Classic and Deck. A member sees the name, the image address, the resources, the status and a note that a machine is assigned, and never a machine name, a machine id, an address, a host key or a registry reference (`machine_name` and `node_id` are null, `machine_assigned` says whether one is set); every write is `owner_required` (403), checked before any body is read. Compute itself is one entry for everyone in both looks: the Deck bar and the Classic account menu (and palette) both list "Compute" for every member; the owner-only Compute map stays a separate entry. A personal access token, even sent with the owner's cookie, is `owner_required` on every workspace route, reads included. Someone signed out is `sign_in` (401). A record of another workspace does not exist in this store, so it is `not_found` (404); this matches the rest of `/api/compute`. Create, edit and discard are audited in the append-only audit table.

**REST.** `GET /api/compute/workspaces` (list, newest first, at most 100, with `can_manage` and `total`), `GET /api/compute/workspaces/<id>`, `GET /api/compute/workspaces/images` (curated list, ranges, defaults, `presets`, `max_workspaces`, `registry_logins`), `POST /api/compute/workspaces` (create; optional `request_id`), `POST /api/compute/workspaces/<id>` (edit: changed fields plus `expected_revision`), `POST /api/compute/workspaces/<id>/discard` (`expected_revision`), `POST /api/compute/workspaces/<id>/credential` (always refused for now). No MCP tool: Compute has none, and this slice does not invent one.

**Error contract.** Every refusal on these routes (any path under `/api/compute/workspaces`, including a malformed one) is `{"error": <code>, "reason": <reason>}` plus `"field"` when it is about one form field; the browser words each (field, reason) pair beside its field or, without a field, in the form summary. Other Compute routes keep their fixed bare shape. The path is decoded before any decision, so an encoded segment (`/%77orkspaces`) is the route it really is. The owner check comes first, then a foreign record is concealed, then the body is read. Codes:

- 400 `invalid_request`: `identifier` (the id in the path is not an identifier), `query` (a query string or fragment), `request` (the shared write boundary refused the request: origin or framing), `body` (not bounded JSON), `unknown_field`, `required` (field named), `no_changes`, `invalid` (`request_id`, `expected_revision`), and per field: `name` (`length`, `characters`, `no_letter`), `image` (`empty`, `too_long`, `scheme`, `characters`, `digest`, `tag`, `registry`, `registry_private`, `registry_no_path`, `name`, `not_curated`), `image_source` (`choice`), `cpu_cores` / `memory_mib` / `storage_gib` (`not_a_number`, `range`, `step`; a huge integer is `range`, never a server error), `network` (`choice`), `node_id` (`choice`), `private_registry` (`choice`, `unavailable`).
- 401 `sign_in` / `session`; 403 `owner_required` / `member` (the caller is not the owner person; a personal access token never is); 404 `not_found` / `record` (no such record in this workspace), `route` (no such path) or `node_id` / `unknown_machine`; 503 `authority_unavailable` / `authority`.
- 409 `conflict`: `name_taken` (`name`), `stale_revision`, `machine_locked` (`node_id`), `limit_reached`, `request_reused` and `request_discarded` (`request_id`), `already_started`, `registry_logins_unavailable`.

**Schema and migration.** Columns and tables added after the first release (`name_key`, `request_id`, `request_hash`, `version`, the tombstone table and its triggers) are added by `workspaces.schema`, which runs once per database: `PRAGMA user_version` records the step done (`SCHEMA_VERSION`), so an ordinary Compute transaction pays for one read. The backfill fills `name_key` for existing rows (keeping stored names unique by key) and `version` from `revision`. The list and the detail read the machine's name in the same query (a JOIN), not one lookup per row.

**UI.** A "Cloud workspaces" section opens the Compute management screen in Classic and Deck (one shared module, `commonplace/web/static/compute-workspaces.js`). The section defines a cloud workspace once. Rows show the name (a heading), one plain status and one resource line; the row's buttons name their workspace ("Details for Build box"); a panel (form, review, details, discard) replaces the row it is about. The form has name, image (curated choices plus "My own image…" with an address field, a real example and a plain definition of "image"), CPU cores, memory in GiB, storage, network and machine ("Choose later" or an enrolled machine with "not checked yet" where it is not verified). Required fields are marked and defaults are stated in each hint. Each field validates inline with its range and the reason; a field's error sits in `aria-describedby` of its own control and carries no live-region role, and one summary alert at the top of the form says "Fix the highlighted fields, then review again." The resource preview ("2 CPU cores, 4 GiB memory, 20 GiB storage on Build machine") shows "Fix the highlighted fields to see what this will use." while a resource value is invalid and always uses GiB. A confirmation after saving is a status line that takes focus; Escape closes a panel; closing returns focus to the button that opened it. On the phone the inputs are 16px, every target is at least 44px, the form's actions are sticky above the tab bar and the page keeps room for the bar. Control borders in Deck are at least 3:1 against their surface. Lists and detail never render empty: every state has a sentence, and the empty-state sentence is hidden while a form is open. Coworkers are called Coworkers. Members see the same list and detail without any edit control and with a sentence saying who can change it.
