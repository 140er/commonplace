### Persistent previews, review round 2 (server and serving)

- **The limit that was hit is named.** Two refusals replace one: `workspace_quota_full` ("already serves 25 previews", next step: stop a preview, which frees a slot) and `workspace_space_full` ("used its 500 MiB", next step: stopping does not free space, the workspace owner can use Delete files on the preview's card to free storage). When both would be passed, the space is named, because stopping alone would not help. Both are 409.
- **The key is told to the person.** The sign-in page says that opening a preview gives its address a key for 30 minutes, that anyone with the exact address can open the preview until then, and to share the preview, not the address; the ready row and the Coworker's publish reply say the same in a sentence. **Why a key is not reused:** a key is stored only as a digest, so an earlier key cannot be handed out again without keeping it in readable form, which would make a database copy worth stealing; a new key per visit stays, with at most three live keys per person and preview. The one line under the card's list is a card-side change.
- **Inline scripts and styles are allowed (decision).** The file policy adds `script-src 'self' 'unsafe-inline'` and `style-src 'self' 'unsafe-inline'`. A Coworker's natural page is a single file with inline style and script, which rendered unstyled and inert under the earlier policy. The sandbox (opaque origin, no network, no form posts) is the isolation, and an inline script can do nothing a script file in the same bundle could not. `unsafe-eval` stays refused and no top-navigation flag was added. The tool text says previews are static, run isolated and need relative links.
- **Stale failure details.** A refused file and kind are cleared when a later publish succeeds and when a later failure is not about one file (storage), so a row never shows an old file name next to a new reason.
- **File names are scanned too.** A path that looks like a credential is refused with the kind only (`contains_secret_like_text`, no file); the name is never stored or shown, because a path is shown to everyone who can open the card.
- **A Coworker cannot reopen what a person stopped,** also when it calls the service directly (`person_stopped`), not only through publishing.
- **Words.** The being-published page says to reload it or open the card (it does not refresh itself); a person who is not the owner is told "Only the workspace owner can change this rule."; the rule sentence has one "or" and says "whichever comes first" when both parts are set; the Coworker tools say "version" for a revision, "previews served", KiB for small sizes and the 30-minute key instead of "never public".
- Not changed here: the session write check (JSON content type and same origin) covers `POST`, `PATCH` and `DELETE` but not `PUT`, which several settings routes also use, so closing it touches routes outside previews and is its own item (card #627). Today a browser cannot send a cross-site `PUT` at all: it needs a CORS preflight and the gateway grants none.
