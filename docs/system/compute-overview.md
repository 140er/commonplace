### Compute overview: every machine, runner and cloud workspace in one place, with honest status, health and usage

One screen in the app shows everything Compute runs on: the **machines** a workspace can be placed on, the **runners** that run Coworkers, and the **cloud workspaces** people created. Each item has a status in plain words, a health line that says when Commonplace last heard from it (never "running" on old data), usage where something reported it (and "not reported" where nothing did), recent activity, and what would stop a Coworker from starting there. The owner can ask for a cloud workspace to start, stop or restart and for a runner to drain, each behind a confirmation that says what it will do, including what happens to work that is running. Members read the same screen and can change nothing. Nothing here needs SSH. This note is the design; slice 1 delivers the read-only screen and the server side of the actions (state machine, owner-only API, confirmation data); slice 2 wires the buttons.

#### What Compute already has (gap analysis, develop at the start of this slice)

- **Runner machines** (`commonplace/runner/registry.py`, table `runner_machines` in the control database): label, `enabled`, `revoked_at`, `binding_state` (`unbound` or `owner_attested`), `max_in_flight` (1 to 4), `max_starts_per_hour`, grant fields. There is no status, last-seen, version or resource column. `GET /api/runners` (`owner_api.py`) lists them for the owner only (members, agent tokens and machine tokens get 403). Enabling and disabling is `PATCH /api/runners/<id>` with `If-Match: <grant_version>`; revoking is one-way. A disabled machine gets 404 on every route (it cannot even report back), so disabling is not a drain.
- **Liveness** is derived only. The machine's own credential records `connections.last_used_at` on each authenticated call (60 second resolution, `control_db.py`); the chat relay records `chat_runners_seen.seen_at` on a chat lease; a started run bumps `runner_jobs.updated_at`. `commonplace/topology/status.py` turns these into `up`, `degraded`, `down` or `unknown` with a reason (`heartbeat`, `late_heartbeat`, `no_heartbeat`, `never_reported`, `disabled`, `revoked`, `start_in_progress`) and the time of the newest signal (`machine_status`, `collect_signals`, thresholds 180 s and 900 s, `StatusConfig`). The map and the Deck status line use it, but `GET /api/topology` drops the reason and the time (one word per node), so no screen can say "last seen 4 minutes ago". The Deck map (`deck-compute.js`) falls back to `GET /api/runners` and shows an enrollment fact (`enabled`, `binding_state`) that is not liveness.
- **Usage that exists:** `runner_resources` (`capacity.py`: `memory_available_mb`, `cpu_free`, `memory_floor_mb`, `reported_at`; stale after 600 s, null means unknown) is stored but read only by start admission, never shown. Running work per machine is `runner_jobs` rows in `leased`, `starting`, `uncertain` and `started`; no endpoint aggregates it per machine (`jobs.lease` counts it for `max_in_flight`). Spend is `run_ledger` joined to the latest `cost_events` row per run (`ledger.py`, `costs.py`): `machine_id` is on every row, a run with no known cost is counted as unknown, never zero, money is summed per currency. `GET /api/costs` groups by agent, project, board and card, not by machine. There is no disk, network or GPU metric anywhere and nothing is measured per cloud workspace.
- **Control channel:** pull only. A runner polls `lease`, `stop` and `sessions/lease` (`runner_api.py`, `agent.py`); the hub never pushes. A card run stop is a request that stays `started` until the machine confirms with terminal evidence (`jobs.cancel`, `stop.py`, `machines-launched-cancel.md`). Revoking or disabling a machine cancels queued and leased runs and makes starting runs `uncertain`; it does not touch started work. There is **no drain**: `max_in_flight` cannot go below 1 and nothing refuses new leases while letting started work finish.
- **Compute targets** (`commonplace/compute/control.py`, table `nodes`): an SSH-reachable machine with name, board, address, interface and a `state` of `pending_verification` or `verified` (set only by the trusted enrollment seam, valid for at most an hour: `enrollment_verifications`). No last-seen, probe or usage field exists, and nothing links a target to a runner machine (the topology `runner_id` fact is separate). `GET /api/compute` is owner-only and its only live bit is `capabilities.transport`.
- **Cloud workspace records** (`commonplace/compute/workspaces.py`, `docs/system/compute-workspaces.md`, #614): name, image, limits, network, optional target machine, `state` (`pending`, `ready`, `failed`), `revision`, `applied_revision`, `version`. `Store._set_workspace_state` is the seam the lifecycle code was meant to write through; nothing calls it. Every record says "Not started". The list and detail are readable by members without machine names.
- **Status pages** (`docs/system/status-page.md`, `compute-status-line.md`, `deck-compute-map.md`): the status page (`web/status.py`) has skills, the bridge and cost sums and no machine or runner data; the Deck status line classifies runs as running, waiting or stuck per runner machine (`deck-compute-work.js`). Neither shows a machine list with health, and neither can act.
- **UI:** `compute.js` serves the Classic `#/compute` screen and the Deck Management tab; `createWorkspaces` (`compute-workspaces.js`) is the cloud workspace section. Nothing in Compute polls; the Classic map polls every 5 s.

**What is missing** for "one overview where a person sees every machine, runner and cloud workspace with live status, health, usage and can start, stop, restart or drain with a confirm and effect preview, without SSH": (1) one read that joins the three kinds and keeps the reason and the age of every signal; (2) a status vocabulary that never says "running" without a fresh report; (3) running-work and spend per runner (the data exists, no reader); (4) the resource report shown with its age; (5) a workspace lifecycle (start, stop, restart) as a state machine with a request path and an executor seam; (6) a drain for runners that the hub itself enforces; (7) confirmation data (what it does, what happens to running work) before any action; (8) a per-item "what blocks a Coworker from starting here" list; (9) per-item recent activity; (10) a screen for all of it in Classic, Deck and on a phone.

#### Decisions

**Three kinds of item.** `machine` is a Compute target (`nodes`): where a cloud workspace is placed. `runner` is an enrolled runner machine (`runner_machines`): where Coworkers run, with a heartbeat. `workspace` is a cloud workspace record. They are listed separately because no link between a target and a runner machine exists; the screen says so where it matters ("Commonplace does not check target machines") instead of guessing a pairing.

**Where each fact comes from.** Everything is read from data the hub already keeps; the overview never opens a connection to a machine, never reads custody and never probes.

| Item | Status and health | Usage | Activity |
| --- | --- | --- | --- |
| runner | `topology.status.machine_status` over `collect_signals` (last signal, its source and age), plus drain and approval from the registry | running runs and `max_in_flight`, starts in the last hour and the hourly cap, the latest resource report with its age, spend for the last 30 days per currency with the count of runs whose cost is unknown | the newest runs of the machine (`runner_jobs`) and drain changes |
| machine (target) | `nodes.state` and the verification window | none collected: "not reported" | owner actions on the target (`audit`) |
| workspace | `cloud_workspaces` plus `cloud_workspace_lifecycle` | the configured limits; measured usage is "not reported" (nothing measures it) | `audit`: created, edited, start/stop/restart requested, withdrawn, executor reports |

**Honest unknown and offline.** Every status says what is true and what it rests on.
- A runner is **Online** only when its newest signal is at most 180 s old, and the line beside it says "Last seen 40 seconds ago: its last contact with Commonplace, not a live check". 180 to 900 s is **Slow to report**, older is **Offline** ("not heard from for 25 minutes; running work may be unaffected, new runs would wait"), no signal ever is **Never connected**, `disabled` and `revoked` say so. Busy is shown beside Online (not instead of the age) when runs are in progress. The thresholds are the topology ones (`StatusConfig`) and are served with the screen.
- A cloud workspace phase reported by a machine (`starting`, `running`, `stopping`) is trusted for 600 s after its last report (the same window as `runner_resources`). After that the status is **Unknown**, with "last reported Running 14 minutes ago, nothing newer". `stopped`, `failed` and `not started` are facts that do not expire and carry their time ("Stopped 2 hours ago").
- Usage values are `{known: false, reason}` when nobody reported them, never 0 and never blank; the screen words each reason ("Not reported: this machine has not sent a resource report", "Not collected for target machines", "Not measured yet for cloud workspaces"). A resource report older than 600 s is shown as "last reported N minutes ago" and called stale.
- A runner whose spend includes runs of unknown cost says "plus N runs with unknown cost", never a total that looks complete.
- A hidden kind is said, not silently empty: a member sees "Machines and runners are visible to the workspace owner".

**Polling, not push.** The screen reads once when it opens, then every 30 seconds while the page is visible (`refresh_seconds` is served, minimum 15), stops while the page is hidden or a confirmation is open, and has a Refresh button that always reads at once. It shows "Updated 12 seconds ago" and says when a refresh failed ("Could not refresh; showing the data from 10:42"), keeping the old data marked as old. The hub has no channel to push to the browser for this data, and the machines are polled by design (15 to 300 s), so a faster interval would only show the same numbers. A refresh never moves focus, never rebuilds an open detail or dialog, and its announcements are polite and only on a change of status.

**The cloud workspace state machine.** Phases (`cloud_workspace_lifecycle.phase`): `not_started`, `starting`, `running`, `stopping`, `stopped`, `failed` (with a reason from `FAILURE_REASONS`). Orthogonal facts: a pending **request** (`start`, `stop` or `restart`; `requested_at`, who asked), `restart_needed` (the existing rule: applied revision behind the saved one, shown as "running with older settings", not a phase) and the time of the last executor report. Allowed moves:

| From | Request needed | To | Who moves it |
| --- | --- | --- | --- |
| `not_started`, `stopped`, `failed` | `start` or `restart` (from `failed`) | `starting` | executor, after it claims the request |
| `starting` | | `running` or `failed` | executor report |
| `running`, `starting`, `failed` | `stop` | `stopping` | executor, after it claims the request |
| `running`, `failed` | `restart` | `stopping`, then `starting` | executor |
| `stopping` | | `stopped` | executor report |
| `running` | | `failed` | executor report (out of memory, storage full, machine unreachable, ...) |

Everything else is refused with a reason (`already_running`, `already_stopped`, `not_started`, `not_running`, `request_pending`, `no_machine`, `needs_credential`). The owner's API call only ever records a **request**; only the executor seam (`workspace_lifecycle.claim` and `report`) changes a phase. The status shown while a request is waiting is **Start requested** (or Stop requested, Restart requested): "Commonplace has saved the request. No machine has picked it up, so nothing is starting yet". Until an executor exists (`executor.available` is false in this version and the screen says so) a request waits; the owner can **withdraw** it at any time before an executor claims it. This slice ships the control path to the requested state and the executor seam, tested with a fake executor, and no sentence in the app says a workspace runs when no executor has reported it; a real container start on a machine belongs to the lifecycle slice that adds the executor. The seam has no REST path.

**The control channel.** The hub has no way to push to a machine, so the executor works the same way runners do: it pulls. `claim(conn, executor_id, now)` hands the oldest unclaimed request to the executor and moves the phase to `starting` or `stopping`; `report(conn, workspace_id, phase, reason, now, claim_seq)` records what the machine did. A report for a request that was withdrawn, replaced or already finished is refused (`stale_claim`) and changes nothing. Reports also refresh `reported_at` (the freshness above). When a start is reported `running` the executor passes the revision it applied, which is how `applied_revision` and `ready` stay consistent with the older record (`Store._set_workspace_state` is called in the same transaction).

**What a stop does to running work.** Stated before the confirm, from facts of the design, never promised beyond it:
- Cloud workspace stop: the Coworker work running inside it is **cancelled, not finished**: the container is asked to stop, given 30 seconds, then ended. Files in its storage volume are kept; processes, open sessions and anything not saved to the volume are lost. Restart is stop followed by start with the same rule. Which work is running inside a cloud workspace is not tracked yet, so the confirmation says "Work inside it is cancelled" without a count and does not claim to know what it is.
- Runner drain: **no new card runs start** on that runner (the hub stops handing it queued runs; they wait in the queue). Runs that already started **finish** normally. Chat sessions and orchestrator sessions are not affected in this version, and the confirmation says so. The runner process itself is not stopped: the hub cannot reach the machine, so starting or stopping the program is outside this screen. Resume undoes the drain; a drain is shown as **Draining** while runs are in progress and **Drained** when none are.
- Every workspace confirmation also says whether a machine can carry the action out right now (`executor.available`).

**Drain is real and enforced by the hub.** The runner's start path already asks `capacity.available` how many more runs may start; a drained machine answers 0 (table `runner_drain` in the runner store, read in the same transaction as the lease). Queued runs stay queued, nothing is cancelled, and `board_capacity` reports 0. Drain is refused for a revoked machine (`revoked`). Disabling a machine (the older control) is unchanged.

**Idempotency and concurrency (as in #614).** Each item carries a `basis`: `seq` (a counter bumped by every accepted request and every phase change; for a runner, the drain counter) and, for workspaces, `version`. The confirmation read returns the basis; the action must send it back as `expected_seq` (and `expected_version`). A stale basis is `409 conflict` / `stale_state` and changes nothing: the owner reloads and sees what changed. A `request_id` (1 to 64 letters, digits, `-`, `_`) makes a retry after a lost answer safe: the same id with the same action returns the same request (200, `repeated: true`, no second request, no second audit row); the same id with another action is `request_reused`. Asking for the action that is already pending (start while a start is pending), draining a runner that is already draining and resuming one that is not draining are repeats too (200, `repeated: true`), not errors. Any other workspace action while a request is pending is `request_pending`. A request that a machine has picked up can be withdrawn only when the machine has stopped reporting (older than 600 s); otherwise `already_picked_up`.

**Who can do what.** The owner reads everything and acts. A member of the workspace reads the overview and a cloud workspace's detail and sees **only cloud workspaces**, with the same redaction as #614: no machine name, no machine id, no address, no runner label, no spend; `can_manage` is false and no action is offered. Machines and runners are owner-only (`hidden` says so). A personal access token is never accepted, as for every Compute route. Every write is `owner_required` / `member`, checked before the body is read; a record of another workspace is `not_found` before anything else is said. Every refusal carries a `reason` (and `field` when it names one), as on the cloud workspace routes. Every action is audited (`workspace.start_requested`, `workspace.stop_requested`, `workspace.restart_requested`, `workspace.request_withdrawn`, `runner.drain_started`, `runner.drain_ended`).

**What blocks a Coworker from starting there.** `health.blockers` lists reasons in plain words, each with the next step: a runner that is revoked, disabled, not approved for work (`binding_state` unbound), draining, full (running runs equal `max_in_flight`), at its hourly cap, silent for more than 900 s or never connected; a cloud workspace with no machine, a stored private image, a machine that is not verified, or no executor in this version. A machine with no blocker says "Nothing is blocking new work", and a machine whose liveness is unknown says "Not known: no recent signal" instead.

**REST.** All under `/api/compute/overview`, owner-or-member read, owner write, no query strings.
- `GET /api/compute/overview`: `{as_of, refresh_seconds, thresholds, can_manage, executor, counts, items, hidden, truncated}`. `items` is every item of every visible kind (at most 100 of each), each `{kind, id, name, subtitle, status: {code, tone, label, detail}, last_seen, health: {state, blockers, issues}, usage, placement, basis, actions}`. Filtering by kind and status is done in the app.
- `GET /api/compute/overview/<kind>/<id>`: the item plus `activity` (newest first, at most 10) and `facts`.
- `GET /api/compute/overview/<kind>/<id>/preview/<action>`: the confirmation data: `{allowed, refusal, title, effect: [...], running_work, will_not: [...], confirm_label, danger, basis, executor}`. Read-only.
- `POST /api/compute/overview/<kind>/<id>/<action>` with `expected_seq`, `expected_version` (workspaces) and `request_id`. Actions: workspaces `start`, `stop`, `restart`, `withdraw`; runners `drain`, `resume`. Answer `{item, request, repeated}` (202 for a new start, stop or restart request, which is only a request; 200 otherwise).
- Refusals: 400 `invalid_request` (`identifier`, `query`, `body`, `unknown_field`, `required`, `invalid` with the field), 401 `sign_in`, 403 `owner_required` / `member`, 404 `not_found` (`record`, `route`), 409 `conflict` (`stale_state`, `request_pending`, `request_reused`, `already_running`, `already_starting`, `already_stopping`, `still_stopping`, `already_stopped`, `not_started`, `not_running`, `no_machine`, `needs_credential`, `revoked`, `nothing_to_withdraw`, `already_picked_up`); the preview of an action that would be a repeat (drain while draining) says so with `already_draining` or `not_draining`, 503 `authority_unavailable`.

**The screen (slice 1: read-only).** One section, "Overview", at the top of the Compute screen in Classic and in the Deck Management tab (module `commonplace/web/static/compute-overview.js`, mounted by `compute.js`; the cloud workspaces form section stays below it). A summary line ("2 online, 1 offline, 3 cloud workspaces, 1 needs attention"), filters by kind and by status (real controls, with counts), a list of rows each with name, kind, one status chip with a sentence, one health line ("Last seen 40 seconds ago"), one usage line, and a Details button that opens the item's detail in place (focus returns to the row's button on close). States: loading, empty (with what to do), error with retry, a filter with no match (with "Clear filters"), offline, unknown, failed, a member's reduced view, and "Updated N seconds ago". Phone: one column, 44 px targets, 16 px inputs, filters in a horizontal scroll row that never traps vertical scrolling. The overview shows what the server's `actions` say and, in slice 1, offers no buttons that change anything; the confirmation and effect preview data exist on the API for slice 2.

**Schema and migration.** `cloud_workspace_lifecycle` is created by `workspace_lifecycle.schema` (one `CREATE TABLE IF NOT EXISTS`, explicit literal SQL, foreign key to `cloud_workspaces` with `ON DELETE CASCADE` so a discarded record leaves no request behind) when the Compute store opens, like the other cloud workspace tables. `has_started` also treats any lifecycle phase other than `not_started` as started, so a workspace that is starting can never be discarded or moved to another machine. `runner_drain` is created in the runner store by `drain.ensure` and read only when it exists. Nothing is dropped and no existing column changes.

**Not in this slice (stated, not hidden).** Starting or stopping the runner program or a container for real (there is no executor yet), measured per-workspace usage (CPU, memory, disk), container logs (the activity list is the audit trail and the run history, not logs), pairing a target machine with a runner machine, a spend or CPU history chart, and push updates.
